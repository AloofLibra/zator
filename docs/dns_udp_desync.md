# Дурение перехвата DNS (UDP:53) через nfqws2 + Lua

Концепт (август 2026). Реализация: [`lua/dns-clone.lua`](../lua/dns-clone.lua).
Интегрирован в zator как профиль 10 (тумблер — пункт 8 главного меню, выбор
стратегии — пункт 1 → профиль 10, WebUI-карточка «DNS Антиспуф»). Ручная
установка из раздела 3 остаётся актуальной для машин без zator.

---

## 1. Проблема

ТСПУ провайдера перехватывает исходящие DNS-запросы по UDP на порт 53 (к любому
резолверу, включая 8.8.8.8) и подменяет/ломает ответы на «неугодные» домены.

Типичная картина на VPS (сервер за ТСПУ):

```
# nslookup deb.torproject.org 8.8.8.8
** server can't find deb.torproject.org: NXDOMAIN     <- подмена: инъекция NXDOMAIN

# nslookup yandex.ru 8.8.8.8
Name:   yandex.ru Address: 77.88.44.55 ...             <- «ненужные» домены проходят
```

Как убедиться, что это подмена по UDP:53, а не реальный ответ резолвера:

```bash
dig +short deb.torproject.org @8.8.8.8                    # UDP - подменяется
dig +tcp +short deb.torproject.org @8.8.8.8               # TCP - обычно НЕ подменяется
curl -s "https://dns.google/resolve?name=deb.torproject.org&type=A"   # DoH - не подменяется
```

Если по TCP и DoH адрес есть, а по UDP приходит NXDOMAIN/0.0.0.0/мусор — это ТСПУ.

---

## 2. Как работает техника «клон с малым TTL»

Идея из удалённой статьи на Хабре, доработанная под nfqws2.

Таймлайн одного DNS-запроса (клиент → резолвер 8.8.8.8):

1. nfqws2 видит исходящий DNS-запрос (UDP, dport 53).
2. Отправляет **клон** запроса:
   - **низкий TTL** (по умолчанию 4): клон доходит до ТСПУ (первые хопы маршрута),
     но умирает задолго до резолвера;
   - **изменённый transaction ID** (`orig XOR 0x8000`): метка, по которой ответ
     на клон отличается от ответа на настоящий запрос.
3. Сразу за клоном выпускается **настоящий запрос**, нетронутым, с нормальным TTL.
4. ТСПУ, увидев «первый» запрос (клон), отвечает фейком. Фейк возвращается клиенту
   с **клоновым** ID.
5. nfqws2 дропает входящий ответ с клоновым ID (инстанс работает и на входящем
   направлении). Даже если не дропнуть — клиент сам отбросит ответ с чужим ID.
6. Настоящий запрос доходит до резолвера, настоящий ответ (с правильным ID)
   проходит к клиенту без изменений.

### Зачем метка ID (отличие от схемы из статьи)

В статье клон предлагался идентичным. Тогда фейковый ответ ТСПУ неотличим от
настоящего: тот же порт, тот же transaction ID — и фейк просто выигрывает гонку
(ТСПУ ближе, чем резолвер). Помеченный клон решает проблему: фейк опознаётся
и отбрасывается, причём двумя независимыми уровнями (клиент + nfqws2).

### Если ТСПУ отвечает не только на первый запрос

Некоторые ТСПУ спуфят **каждый** запрос потока, а не только первый. Тогда фейк
с правильным ID всё равно приходит. Против этого в наборе есть стратегии без
клона, ломающие саму возможность спуфа:

- **паддинг запроса** (`udplen`): резолверы обязаны игнорировать мусор в хвосте
  пакета, а парсер ТСПУ может не справиться и не ответить;
- **IP-фрагментация запроса** (`ipfrag_pos_udp=8`): вопрос домена уезжает во
  второй фрагмент, stateless-ТСПУ не собирает фрагменты и не видит qname;
- **паддинг клона** (`pad=`) и **пауза оригинала** (`send:delay` + `drop`).

Перебор стратегий (раздел 4) сам покажет, какой тип у вашей ТСПУ.

## 3. Установка на машину с zapret2/zator

### 3.1. Файл Lua

```bash
cp lua/dns-clone.lua /opt/zapret2/lua/dns-clone.lua
```

Путь может быть любым — файл грузится по абсолютному пути через `--lua-init`.

### 3.2. Правки `/opt/zapret2/config`

1. Добавить порт **53** в UDP-порты (правила заворачивания строятся из этой
   переменной, в обе стороны — исходящие по dport, ответы по sport):

```bash
NFQWS2_PORTS_UDP=...,53          # существующий список + ",53"
```

2. Проверить, что ответы вообще заворачиваются (лимит reply-пакетов на поток):

```bash
NFQWS2_UDP_PKT_IN=3              # >=1, дефолтное значение
```

3. В многострочный `NFQWS2_OPT="..."` добавить загрузку скрипта (рядом с другими
   `--lua-init`, порядок не важен) и блок стратегий из раздела 4.

### 3.3. Проверка правил заворачивания

Стандартные правила создают и обратное направление по sport 53:

```bash
iptables-save | grep -E "sport (53|dport 53" | grep -i nfqueue
nft list ruleset | grep -E "udp (d|s)port 53"
```

Если обратного правила нет (ответы не доходят до nfqws2 — дроп фейков работать
не будет, в логе не будет `dnsclone: dropping spoofed response`), добавить вручную:

```bash
# номер очереди взять из запуска nfqws2: ps ax | grep nfqws2 | grep -o 'qnum [0-9]*'
iptables -t mangle -I INPUT -p udp --sport 53 \
  -m connbytes --connbytes 1:3 --connbytes-dir reply --connbytes-mode packets \
  -j NFQUEUE --queue-num <QNUM> --queue-bypass
```

### 3.4. Перезапуск

```bash
systemctl restart zapret2        # или: /opt/zapret2/init.d/sysv/zapret2 restart
```

Ошибки Lua-скрипта видны в `/tmp/nfqws2_1.err` (Entware) или в journalctl/logread.

## 4. Готовый блок стратегий

Вставить внутрь `NFQWS2_OPT="..."` отдельным профилем (после существующих
блоков, перед закрывающей кавычкой).

**ВАЖНО: опции внутри `NFQWS2_OPT` нельзя комментировать через `#`.**
Config сорсится шеллом, `NFQWS2_OPT` передаётся nfqws2 как поток слов argv
(без кавычек), а GNU getopt переставляет не-опции в конец и продолжает разбор:
токен `#` просто игнорируется, и `--lua-desync=...` со следующей «закомменти-
рованной» строки становится **живой опцией**. Строка `# --lua-desync=send:...:delay=3`
создаёт работающий инстанс send с delay=3 — отсюда ошибки «invalid timer
period. must be >=10 ms» (а если бы она не падала, последующий «закомменти-
рованный» `drop` убил бы весь DNS). Безвредны только текстовые комментарии
без `--...`-токенов — так устроен и `config.default` zator: маркеры и подписи,
но никогда закомментированные опции.

Правило: в блоке держать **только строки активной стратегии**. Смена стратегии =
заменить строку в конфиге на вариант из каталога ниже и перезапустить сервис.
Убрать опцию = удалить её из `NFQWS2_OPT`.

```
--lua-init=@/opt/zapret2/lua/dns-clone.lua

--new
# Антиспуф DNS UDP:53 (текст допустим, опции комментировать нельзя)
--filter-udp=53
--in-range=-d100
--out-range=-d100
--payload=dns_query,dns_response
--lua-desync=dnsclone:ttl=8:ip_id=rnd:resend=1
```

Диапазоны всегда задавайте явными и ограниченными (`-d100`), а не `a`
(рекомендация upstream-разработчика zapret2): `a` — бесконечный диапазон без
верхней границы, при блоках ниже по конфигу это чревато проблемами, и Lua
вызывается на каждый пакет потока без cutoff. Для однопакетных DNS-потоков
`-d100` покрывает всё с запасом. В живых тестах работал и вариант с `a`,
но явные границы — правильный стиль.

Каталог стратегий — заменить последнюю строку блока на один из вариантов:

| # | Строка(и) вместо последней | Что делает / когда пробовать |
|---|---|---|
| 1 | `--lua-desync=dnsclone:ttl=4` | базовая: клон с TTL 4 + метка ID + дроп ответов по метке |
| 2 | `--lua-desync=dnsclone:ttl=2` | клон с TTL 2 (ТСПУ в первых 1-2 хопах) |
| 3 | `--lua-desync=dnsclone:ttl=8` | клон с TTL 8 (ТСПУ дальше, либо спуф на хопе провайдера). Подтверждено на VPS за ТСПУ: ttl=4 не доезжал, одиночный клон ttl=8 снял подмену |
| 4 | `--lua-desync=dnsclone:ttl=4:pad=8` | клон + 8 нулевых байт в хвосте (ломает строгие парсеры ТСПУ) |
| 5 | `--lua-desync=dnsclone:ttl=4`<br>`--lua-desync=send:dir=out:delay=10`<br>`--lua-desync=drop:dir=out:payload=dns_query` | клон + оригинал уходит с паузой 10 мс (дропается и пересылается таймером). 10 мс — минимум таймеров nfqws2 |
| 6 | `--lua-desync=udplen:payload=dns_query:increment=8:pattern=0x00000000` | без клона: паддинг настоящего запроса +8 байт |
| 7 | `--lua-desync=send:dir=out:ipfrag:ipfrag_pos_udp=8`<br>`--lua-desync=drop:dir=out:payload=dns_query` | без клона: IP-фрагментация запроса, вопрос во 2-м фрагменте (ipv4) |
| 8 | `--lua-desync=send:dir=out:ip6_destopt`<br>`--lua-desync=drop:dir=out:payload=dns_query` | ipv6: extension header в начале запроса (stateless ТСПУ не парсит) |
| 9 | `--lua-desync=dnsclone:ttl=8`<br>`--lua-desync=dnsclone:ttl=4`<br>`--lua-desync=dnsclone:ttl=2` | веер клонов для неизвестной дистанции до ТСПУ. Все клоны несут одну метку ID (дедуплицируется), фейк на любой из них дропается. Верхнюю границу веера держать ниже расстояния до резолвера (см. 5.1) |
| 10 | любая стратегия + `:ip_id=rnd:resend=1` (напр. `--lua-desync=dnsclone:ttl=8:ip_id=rnd:resend=1`) | вариант для роутеров Keinetic/NDM и универсальный режим: вердиктный оригинал подавляется NDM, поэтому оригинал повторно уходит raw-сокетом с рандомным IP-ID сразу за клоном, вердикт — DROP. На Linux тоже применим: дроп первого пакета конвертится штатным postnat-workaround nfqws2 в пакет-зомби (ip_p=255, ttl=1) — conntrack подтверждается, дубль до резолвера не доходит. Проверено на FORWARD-пути Keenetic вживую: оба пакета исходят, ответы доходят до LAN-клиента, и на реально перехватываемом домене (NXDomain-инъекция у провайдера) с resend приходят НАСТОЯЩИЕ ответы вместо спуфа |

Замечания:

- `ttl=N` в `dnsclone` — шорткат, выставляющий сразу `ip_ttl` и `ip6_ttl`
  (стандартные fooling-аргументы). Можно задавать их по отдельности:
  `dnsclone:ip_ttl=4:ip6_ttl=2`.
- `dnsclone` понимает и другие стандартные аргументы: `repeats=N` (несколько
  копий клона), `badsum`, `ipfrag...` (применяются к клону).
- Стратегии 5/7/8 используют пару `send` + `drop`: `send` шлёт модифицированную
  копию, `drop` глушит оригинал (`dir=out:payload=dns_query` — чтобы не задеть
  входящие ответы).
- Отдельно про `--in-range`: по умолчанию входящие пакеты до Lua не доходят
  (`--in-range=x`), а дроп ответов ТСПУ работает именно на входящих — поэтому
  входящий диапазон нужен, но задавайте его ограниченным (`-d100`), не `a`
  (см. замечание upstream в разделе 4).
- `--payload=dns_query,dns_response` в шапке держит оба направления для
  `dnsclone`; для стратегий паддинга нужный payload задан аргументом в самой строке.

## 5. План тестирования

### 5.1. Подбор TTL

TTL клона обязан удовлетворять ДВУМ условиям одновременно:

- **дойти до ТСПУ**: недолёт — провал, для ТСПУ «первым запросом» станет
  настоящий, спуф уйдёт с правильным ID;
- **НЕ дойти до резолвера** (и до провайдерного DNS-прокси): «перелёт»
  НЕ безвреден. Многие провайдеры держат прозрачный DNS-прокси с
  дедупликацией одинаковых запросов с одного порта — он отвечает только
  первому пакету пары клон+оригинал (клону, ответ дропается по метке),
  а оригинал отбрасывает как дубль. Итог — полный отказ резолва
  (подтверждено живым тестом: ответы шли только на метки, оригинал
  оставался без ответа).

Дистанция до ТСПУ у разных провайдеров разная (1-10 хопов), расстояние до
резолвера обычно 8-15. Рабочее окно: hops(ТСПУ) <= ttl < hops(резолвера).

```bash
traceroute -n 8.8.8.8        # хопы до резолвера - верхняя граница
```

Для неизвестной среды — веер 2/4/8 (стратегия 9); значение 12+ рискованно
(может превысить расстояние до резолвера/прокси). Штатный `ip_autottl` для
DNS не работает: он выводит TTL из incoming_ttl потока, а DNS-потоки
однопакетные (новый src-port на запрос) — incoming_ttl не успевает
накопиться до первого запроса. Только фиксированные TTL.

### 5.2. Базовая проверка (после каждой смены стратегии — рестарт)

```bash
dig +short deb.torproject.org @8.8.8.8        # было: NXDOMAIN / пусто
dig +short habr.com @8.8.8.8                  # контроль "обычных" доменов
```

Успех: заблокированный домен резолвится в реальные адресы (сверить с
`dig +tcp` или DoH из раздела 1), обычные домены не сломались.

### 5.3. Картина в tcpdump

```bash
tcpdump -nn -v -i eth0 udp port 53
```

При работающей стратегии 1 ожидается на один запрос:

1. исходящий запрос, ID=A (настоящий);
2. исходящий клон, ID=A±0x8000, ttl маленький;
3. входящий фейк от ТСПУ, ID=A±0x8000 — **дропается nfqws2** (в tcpdump всё равно
   виден — он слушает до netfilter);
4. входящий настоящий ответ, ID=A, ttl нормальный — проходит.

### 5.4. Логи

Вывод `dnsclone` в DLOG (отладка nfqws2):

```
dnsclone: query clone id 43210 -> 22570
dnsclone: dropping spoofed response id=22570
```

Если подмена есть, а строк `dropping spoofed response` нет — ответы не доходят
до nfqws2 (см. 3.3) или фейк приходит с правильным ID (ТСПУ отвечает на каждый
запрос — см. диагностику ниже).

Известные сообщения и их причины:

```
desync function returned non-int result
desync ERROR. passing packet unmodified.
```

Появлялось в первой версии `dns-clone.lua` (явный `return nil` вместо пустого
`return`; свежие исходники fork-zapret2 трактуют и nil как PASS). Побочные
эффекты при этом всё равно выполнялись, так что стратегия работала, но лог
заспамливался. Фикс от 2026-08-31: все возвраты без вердикта — пустой `return`.
Если сообщения остались после обновления файла — на VPS старая копия
`dns-clone.lua` (перезалейте и перезапустите сервис).

```
LUA ERROR: /opt/zapret2/lua/zapret-antidpi.lua:99: invalid timer period. must be >=10 ms
desync ERROR. passing packet unmodified.
```

Не связано с `dns-clone.lua`: это функция `send` со строкой `delay < 10`.
Запускается, даже если строка стратегии «закомментирована» через `#` —
опции внутри `NFQWS2_OPT` комментировать нельзя (разбор в разделе 4).
DNS при этом работает по случайности: ошибка в `send` обрывает цепочку
инстансов, и следующий за ним «закомментированный» `drop` (который убил бы
все запросы) не выполняется. Лечение: удалить из блока все лишние
`--lua-desync`-строки, оставив только активную стратегию.

## 6. Диагностика неудач

| Симптом | Вывод | Что пробовать |
|---|---|---|
| `LUA ERROR ... invalid timer period. must be >=10 ms` (zapret-antidpi.lua:99) или лишние срабатывания «неактивных» стратегий | В `NFQWS2_OPT` остались «закомментированные» `--lua-desync`-строки — они АКТИВНЫ (см. раздел 4) | Удалить все лишние строки, оставить только активную стратегию, рестарт |
| **ВСЕ домены по таймауту** при включённом dnsclone, в tcpdump ответы приходят только с клоновым ID (меткой) | Провайдерский дедуп-прокси или TTL клона достаёт до резолвера/прокси (см. 5.1) | Уменьшить TTL ниже расстояния до резолвера; не помогло — в пути дедуп-прокси, стратегия неприменима, выключить (DoH/нестандартный порт) |
| То же самое на Keenetic, причём на любом TTL и обоих путях (OUTPUT и FORWARD), даже со штатным `send` — на проводе только клоны, оригиналы не выходят | NDM подавляет вердиктный оригинал, если до него из raw-сокета ушла копия с тем же 5-tuple (дедуп по 5-tuple, IP-ID роли не играет) | Добавить `:resend=1:ip_id=rnd` — оригинал повторно уходит raw-сокетом (проверено на FORWARD: работает) |
| Всё ещё NXDOMAIN, в tcpdump входящий фейк с ID=оригинала | Клон не доехал до ТСПУ (TTL мал) | Стратегии 2→3 (TTL 8), потом 5, потом 9 (веер) |
| Стратегия 1 (ttl=4) одна не работает, раньше работала цепочка клона с разными TTL | ТСПУ дальше 4 хопов — доезжал только клон с большим TTL | Стратегия 3 (ttl=8) или 9 (веер) |
| Всё ещё NXDOMAIN, фейк дропается, но приходит второй фейк с правильным ID | ТСПУ спуфит каждый запрос | Стратегии 4, 6, 7 |
| DNS отвалился полностью (таймауты на всех доменах) | Дропается/ломается оригинал | Убрать стратегии 5/7 (они дропают оригинал); проверить, что правила с `--queue-bypass` |
| Работает, но медленный первый резолв | Пауза delay велика | Меньше 10 мс таймер не принимает — вернуться к стратегиям 1-4 |
| Обычные домены сломались, заблокированные нет | Паддинг/фрагментация не переваривается резолвером | Убрать стратегии 6/7, вернуть 1 |

## 7. Ограничения и риски

- **Коллизия ID**: если клиент отправит новый запрос с ID, равным метке живого
  клона (orig⊕0x8000), его ответ будет ошибочно дропнут один раз. Клиент
  переспросит с другим ID. Вероятность мала, самолечится.
- Клон защищает только **исходящий UDP:53**. DoH, DNS over TLS, нестандартные
  порты и TCP:53 — вне области действия.
- На роутере (не на самом хосте) защищается трафик, проходящий через NFQUEUE
  (обычно LAN-клиенты); собственные запросы роутера могут идти мимо очереди.
- **Keenetic NDM, OUTPUT-путь** (собственные запросы роутера): при rawsend из
  очереди NFQUEUE-вердиктный исходный пакет НЕ покидает роутер — наружу уходит
  только клон (подтверждено и штатным `send`). Для помеченного клона это полный
  отказ резолва. Стратегию на Keenetic проверять только на FORWARDED-трафике
  LAN-клиентов (не протестировано).
- **Провайдерский прозрачный DNS-прокси с дедупликацией**: отвечает только
  первому пакету пары клон+оригинал. Признаки в tcpdump: ответы с
  уменьшенным ttl (55-56 против ~104 у настоящих ответов 8.8.8.8), ответ
  иногда приходит с чужого IP резолвера провайдера. В таких сетях
  клон-first неприменим при любом TTL.
- Среды различаются: дистанция до ТСПУ (1-10 хопов, у каждого провайдера своя),
  поведение (ответ на первый запрос потока vs на каждый), положение dnsmasq
  (если клиенты спрашивают роутер, а dnsmasq форвардит наружу — защищаемое
  плечо начинается на самом роутере, проверить заворачивание OUTPUT при
  интеграции). Рабочий TTL с VPS нельзя переносить на роутеры других
  провайдеров — там нужен веер или свой подбор.
- Если ТСПУ отвечает на каждый запрос и при этом корректно парсит паддинг и
  фрагменты — остаются только DoH/нестандартный порт (штатная рекомендация
  upstream-документации zapret2).
- Клон увеличивает исходящий DNS-трафик вдвое (на один короткий пакет) —
  незначительно.

## 9. Аудит модуля по исходникам zapret2/nfqws2 и живым тестам (2026-08-31)

Аудит по исходникам zapret2 (nfq2/*.c, lua/) и живым тестам: VPS за ТСПУ
(работает), Keenetic (sup-build 4.9-ndm, lua_compat 6, LuaJIT ON MIPS32R2).

1. **Track для UDP-сессий** (`nfq2/conntrack.c`): запись по 5-tuple
   (`ConntrackExtractConn` + `connswap` для обратного направления,
   `ConntrackPoolDoubleSearchPool`), `track->lua_state` — ссылка Lua-registry,
   живёт вместе с записью. `t_last` обновляется на каждом пакете в обе
   стороны (`conntrack.c:222`); таймаут UDP `CTRACK_T_UDP=60` с
   (`conntrack_base.h:9`), purge каждые 10 с. Между запросом и ответом
   (RTT десятки мс) запись стабильна — pending-механизм корректен.
   Новый запрос с нового порта = новая запись; переиспользование порта
   (A+AAAA одним сокетом) = одна запись, pending аккумулируется.
2. **Кэш решения по потоку**: единственный механизм пропуска Lua — флаги
   `b_lua_in/out_cutoff` (`desync.c:955-965`), ставятся только когда ВСЕ
   инстансы ушли в cutoff (добровольно через `instance_cutoff` или по
   превышению верхних границ `--in/out-range`). У блока dnsclone диапазоны
   `a` без верхних границ и добровольного cutoff — **Lua вызывается на
   каждый пакет, кэша нет** (аналог бага #229 отсутствует). Повторный
   запрос с того же порта обрабатывается заново.
3. **Чексумма после паддинга**: `lua_reconstruct_dissect`
   (`nfq2/lua.c:2580-2598`) при каждом rawsend пересчитывает
   `udp->uh_ulen` из фактической длины payload и `udp_fix_checksum(...)`
   с нуля (если не задан `keepsum`). Ручное обновление `uh_ulen` в модуле
   избыточно, но безвредно. Паддинг и замена ID безопасны.
4. **Поля dis и сигнатуры**: `uh_sport/uh_dport/uh_ulen/uh_sum`
   (`lua.c:1392-1398`), `ip_ttl`, `ip6_hlim` — имена актуальны.
   Сигнатуры `apply_fooling(desync,dis,fooling_options)`,
   `apply_ip_id(desync,dis,ipid_options,def)`, `deepcopy(orig,copies)`
   идентичны в обеих версиях бандла (реальный diff между копиями — только
   `luaexec`-обход старого бага `return nil` и TLS-реконструкт-фиксы).
5. **Expire для Lua-состояния**: готового примитива нет (колбэка окончания
   потока нет), но зарегистрирована C-функция `clock_gettime() -> sec,nsec`
   (`lua.c:825`). С версии аудита pending хранит временные метки и
   выселяется по `pending_ttl` (2000 мс по умолчанию) + жёсткий кап
   `pending_max` (16).
6. **Коллизии меток ID**: ложный дроп требует, чтобы клиент выпустил новый
   запрос с ID ровно `orig XOR 0x8000` пока метка жива. Вероятность на пару
   запросов ~1/65536; окно уменьшено до pending_ttl, самолечится ретраем
   клиента. На практике незаметно.
7. **Без ttl-аргументов**: клон уходит с исходным TTL и доходит до
   резолвера. Против answer-once ТСПУ это всё ещё работает (клон проходит
   сквозь неё первым), но на сетях с дедуп-прокси — гарантированный отказ
   резолва. Поведение сохранено (логируется warning), явный ttl обязателен.
8. **Keenetic NDM, OUTPUT-путь (живой тест, 6 раундов бисекции)**: при
   rawsend из очереди исходный вердиктный пакет не покидает роутер —
   на проводе только клон (воспроизводится ШТАТНЫМ `send:ip_ttl=8`,
   без dns-clone.lua). На x86-Linux (VPS) оригиналы выходят. Отсюда:
   модуль на Keenetic применять только к FORWARDED-трафику (не
   протестировано — нужен тест с LAN-клиентом), либо не применять.
   Заодно тест вскрыл, что провайдер автора держит прозрачный DNS-прокси
   с дедупликацией (ответы ttl 55/56 против 104-107 у настоящих, ответ
   habr.com однажды пришёл с 195.208.4.1) — «перелёт» клона до резолвера
   опасен, TTL строго меньше расстояния до резолвера (см. 5.1).
9. **Fastpath/PPE**: очередь на OUTPUT-пути работает (18/18 пакетов дошли
   до NFQUEUE, обработка без потерь — `user_dropped=0`); проблема не в
   обходе очереди, а в подавлении вердиктного пакета после rawsend (п.8).
   Дополнительно проверено: отключение PPE (`ndmc -c "no ppe"`,
   MediaTek, runtime) НЕ влияет на подавление; перестановка NFQUEUE-правила
   в конец цепочки OUTPUT (после NDM-цепочек) НЕ влияет; вердикт-путь форка
   чистый (nfqws.c: NF_ACCEPT с исходной меткой, коммиты 836a891/54f41cf
   касаются только TLS-reasm replay). `send:delay=10` (клон таймером ПОСЛЕ
   оригинала) выпускает оба пакета и DNS работает — подавление строго
   привязано к ситуации "тот же 5-tuple уже ушёл в raw до вердикта"
   (вероятно, NDM-сессии/connskip отбрасывают оригинал как дубль). Вывод:
   на OUTPUT-пути Keinetic стратегия неприменима в принципе (клон-first =
   подавление оригинала, клон-second = проигрыш гонки спуфу). Для
   интеграции в zator (FORWARD-путь, ipset `zport_udp` + connbytes
   1:5/1:3) поведение требует отдельной проверки с LAN-клиентом — там
   весь продакшн zator работает, и подавления скорее всего нет.
10. **FORWARD-тест с LAN-клиентом (2026-08-31, Keenetic, mangle
   POSTROUTING/FORWARD, очередь 299, nslookup с Windows-клиента)**:
   подавление подтверждено и на FORWARD — со штатным `send:ip_ttl=8`
   на проводе только клоны, оригиналы от клиента не исходят, nslookup
   ретранслирует с новых портов и умирает. Гипотеза «NDM дедуплицирует
   по (5-tuple + IP-ID)» опровергнута (`ip_id=rnd` не помогло) — дедуп
   чисто по 5-tuple для первого пакета нового потока. Продакшн-QUIC
   это переживает благодаря ретрансмиссиям клиента на том же порту +
   исчерпанию connbytes 1:5; DNS с новым портом на каждый ретрай — нет.
11. **Решение для роутеров: режим `resend=1`** (добавлен в dns-clone.lua):
   клон и оригинал оба уходят raw-сокетом (клон первым с меткой и малым
   TTL, оригинал следом с рандомным IP-ID), вердикт остаётся PASS.
   Raw-пакеты NDM не подавляет никогда. Живой тест на FORWARD Keenetic:
   клон (ttl 8, ID 32769) → оригинал (ttl 127, ID 1) через 313 мкс →
   настоящий ответ Google (ttl 104) доставлен LAN-клиенту, nslookup
   резолвится. Обратный NAT-путь работает (conntrack-запись потока
   жива, ответы проходят через очередь и доходят до клиента).
12. **Вердикт при resend=1 = DROP** (правка по ревью): обе копии уже
   ушли raw-путем, вердиктный пакет избыточен. Прямой DROP первого
   пакета потока в postnat-режиме конвертится штатным механизмом
   nfqws2 `ct_new_postnat_fix` (desync.c:661): пакет выпускается
   испорченным (ip_p=255, ttl=1) — conntrack подтверждается, но
   зомби-пакет умирает на первом хопе и не создаёт дубль запроса
   на резолвере ни на одной платформе. Живой FORWARD-тест с DROP:
   резолв работает, на проводе 2 пакета на запрос.
13. **Защита от реального перехвата на FORWARD подтверждена (контрастный
   тест)**: базлайн без модуля — `deb.torproject.org` получает
   NXDomain-инъекцию от провайдерского перехватчика; с
   `dnsclone:ttl=8:ip_id=rnd:resend=1` — настоящие CNAME+A/AAAA записи
   Torproject от Google (ttl 104-105), инъекция не приходит вовсе
   (`dropping spoofed` = 0: перехватчик, увидев умирающий ttl-8 клон
   первым, пропускает оригинал чистым). Уточнение к 5.1: on-path
   перехватчик видит клон ДО своей точки дропа по TTL, поэтому клон
   "умирает раньше резолвера" не означает "не доходит до ТСПУ".
15. **VPS-верификация канонической строки (2026-08-31, VPS,
    `dnsclone:ttl=8:ip_id=rnd:resend=1`)**: на проводе ровно ДВА UDP-пакета
    на запрос — клон (ttl 8, метка 47614 XOR 0x8000 = 14846) и
    переотправленный оригинал (ttl 64, rnd IP-ID) через 146 мкс; третьего
    дубля нет (postnat-зомби с proto 255/ttl 1 не является UDP и в
    udp-фильтр tcpdump не попадает). Ответ ТСПУ клону (NXDomain, ttl 59 —
    инъекция с ближнего хопа) дропнут фильтром, настоящий ответ оригиналу
    (CNAME + адреса Torproject, ttl 110) доставлен. Для незаблокированных
    доменов тот же ближний прокси отвечает клону реальными данными из
    кэша (ttl 59) — дропается по метке, клиенту уходит ответ настоящего
    резолвера.
14. **connbytes и raw-пакеты**: raw-клоны/resend идут через OUTPUT-путь
   роутера и не попадают в очередь, собственные conntrack-записи не
   накручивают connbytes FORWARD-потока (эмпирически: reply-лимит 1:3
   не исчерпан, ответы дошли). Для DNS-потоков (один запрос-один
   ответ) неприменимо в принципе; переносить resend-подобную технику
   на длинные потоки других профилей — проверять отдельно.
