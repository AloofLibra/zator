# Переиспользование mawg, MagiTrickle и sing-box-lx

**Статус:** технический аудит для coding-агента, 24.10.2026. Это **кандидаты** для использования; совместимость конкретного Keenetic, его архитектуры, установленных бинарников и текущих веток требует локальной проверки.

## 1. Вывод для реализации

**Рекомендация:** испытать `sing-box-lx` как **отдельный SOCKS5 data-plane процесс** на роутере в TCP-MVP; `mawg` использовать как источник готовых приёмов/адаптеров, а MagiTrickle — **read-only** для выявления конфликтов policy routing. Не вводить обязательную зависимость от этих проектов.

Все три проекта решают **другие задачи**, а не заменяют `nfqws2`:

1. `nfqws2` по-прежнему получает трафик через *изолированную* NFQUEUE и выполняет реальную DPI-стратегию.
2. SOCKS (возможно `sing-box-lx`) создаёт на роутере исходящие TCP-socket'ы по команде браузера на ПК.
3. Router Agent владеет жизненным циклом тестовой сессии, передаёт стратегию в private locks, коррелирует соединения с очередью и подтверждает выполнение.
4. `mawg`/MagiTrickle предоставляют дополнительный *контекст* активных VPN/маршрутов; ни одна проба не должна менять production-пулы/группы.

## 2. Матрица переиспользования

| Проект / часть | Реально найдено в коде или документации | Использовать | Ограничение / проверка |
| --- | --- | --- | --- |
| `sing-box-lx` — стандартный `socks` inbound + `direct` outbound | Форк сохраняет движок sing-box, который поддерживает proxy inbound и direct egress; сборки включают MIPS/MIPSLE/ARM/Linux | **Да, кандидат A**, но **новый отдельный процесс**, отдельный конфиг, UID, PID и порт | На целевой сборке проверить `sing-box check`, фактический TCP path, RAM/CPU и возможность drop privileges |
| `sing-box-lx` — `lxd` | В README и `docs-lx/lxd-daemon.md` описаны daemon, admin REST, gRPC, mTLS и config reload с rollback | **Не требуется в TCP MVP**; можно изучить после | Управляет *sing-box*, не тестовым `nfqws2` и не NFQUEUE; не подменять доказательство применения стратегии gRPC-счётчиками |
| `sing-box-lx` — TUN/routing/QUIC | В форке есть sing-box TUN, QUIC и дополнительные observability-функции (с учётом build tags) | **Исследовать после MVP** | TUN на ПК не создаёт автоматически сервер туннеля на роутере; процессный routing, UDP и безопасность требуют отдельного PoC |
| `mawg` — Keenetic/OpenWrt backends | README: один Go-бинарник, KeeneticOS/Entware + OpenWrt, WebUI/API; исходники `internal/platform/*` | **Да, как reference** | Не считать `internal` пакет публичным SDK; при переносе проверять лицензию и ветки, сохранять независимость агента |
| `mawg` — `internal/rotator/probe_linux.go` | `SO_BINDTODEVICE`, отдельный dialer, HTTP probe без редиректа, диагностируемая ошибка | **Идеи + выборочно код** | `SO_BINDTODEVICE` нельзя слепо применять к SOCKS: выход через нужный WAN нужно подтвердить, а не подменить routing в тесте |
| `mawg` — `internal/magitrickle/client.go` | API `/api/v1/groups`, модели групп, чтение `groups?with_rules=true`; также методы записи и восстановление после сбоев bulk PUT | **Только read-only методы**, необязательная интеграция | Не вызывать `CreateGroup`, `UpdateGroup(s)`, `Delete*`; запись может затронуть рабочие правила |
| `mawg` — health/rotation и VPN-пулы | Нативные WG/AWG и sing-box proxy-пулы, автоматическая ротация, fallback, проверки интерфейсов | **Только диагностика состояния** | Не маршрутизировать пробы через production VPN-пулы: иначе «успех» может быть результатом VPN, а не DPI-стратегии |
| `magitrickle` | README: DNS-перехват, соответствие доменов/IP, policy routing и группы | **Опциональный детектор конфликтов** | Не даёт отдельную NFQUEUE, не применяет стратегию `nfqws2`, может переписать firewall при обновлении правил |

**Порядок проб:** (1) отдельный минимальный `sing-box-lx` на роутере; (2) лёгкий SOCKS-бинарник как fallback, если (1) слишком тяжёлый, нет бинарника под ABI или возникают сложности с выделенным UID.

## 3. Почему нельзя переиспользовать уже работающий mawg/sing-box

- Его рабочий процесс может обслуживать клиентские VPN-пулы, DNС-логику, TUN и routing policies; изменение inbound/outbound или reload для одной стратегии рискует задеть пользовательский трафик.
- Уже запущенный процесс не обязательно имеет **уникальный UID**, по которому Netfilter сможет отличить только тестовые исходящие сокеты.
- Маршрут `direct` внутри sing-box не означает автоматически «в обход всех MagiTrickle-правил и через WAN провайдера»: после выхода сокета из процесса действуют kernel policy routing и mark.
- Отдельный lxd-инстанс с gRPC и mTLS для одной локальной SOCKS-задачи может занять существенно больше ресурсов, чем требуется на роутере со 128 МБ RAM.
- Даже если sing-box возвращает успешный HTTP, нужно независимое доказательство, что пакеты прошли *тестовую* очередь и вызвали тестовую Lua-стратегию.

## 4. Два возможных кандидата на TCP SOCKS runtime

### Кандидат A — отдельный `sing-box-lx`

**Требуемый режим:** loopback `socks` inbound (TCP CONNECT), `direct` outbound, никаких VPN/TUN/selector/urltest/route-правил и auto-reload, только IPv4 в TCP MVP. DNS/resolver должен быть явно задан и задокументирован.

**Шаги агента:**

- [ ] A1. Определить установленные бинарники и версии (`/opt/bin/sing-box`, `/usr/bin/sing-box`), проверить совместимость fork `-lx` и наличие модуля SOCKS в фактической сборке.
- [ ] A2. Сгенерировать тестовый *одноразовый* конфиг, верифицировать `sing-box check -c <path>` — не записывать рабочие конфиги `mawg`.
- [ ] A3. Запустить отдельный процесс под `PROXY_UID`, bind только `127.0.0.1:<port>`; `NFQWS_UID` обязательно отличается. Права и возможность снять root проверять **в реальной среде**.
- [ ] A4. Пропустить из Windows через SSH `-L` локальный SOCKS CONNECT к HTTPS; зафиксировать actual `OUTPUT` UID, source ports, conntrack flow и WAN интерфейс.
- [ ] A5. Измерить RSS/CPU/старт/скорость/количество TCP-подключений с работающими Zator+mawg+MagiTrickle; проверить 128 МБ роутер, если именно он целевой.
- [ ] A6. Убить тестовый sing-box и убедиться, что производственный процесс остался жив, его конфиг/маршруты не изменились. Проверить отдельно остановку mawg и обратно.
- [ ] A7. Если любой пункт не пройден: зафиксировать причину и перейти к B **без пересмотра API агента**.

### Кандидат B — компактный TCP SOCKS

- [ ] B1. Выбрать готовый Entware SOCKS-пакет либо небольшой Go/C сервер; обеспечить IPv4 TCP CONNECT, loopback listener, upstream hostname resolution и отсутствие UDP в MVP.
- [ ] B2. Выделить `PROXY_UID`, ограничить процессы и ресурсы; проверить тестовые исходящие сокеты через `owner` + conntrack.
- [ ] B3. Повторить всю матрицу A4–A6 и сравнить с кандидатом A.
- [ ] B4. Зафиксировать в ADR измерения и причину выбора, а не выбирать движок по названию.

## 5. Интеграция с mawg и MagiTrickle

### Read-only route inspector

Опциональный адаптер, который **не управляет** mawg/MagiTrickle:

- получить сведения об активных туннелях и привязках policy routing из доступных read-only API mawg/MagiTrickle;
- сверить kernel `ip rule`, `ip route`, firewall mark и conntrack с тем, что видно в этих API;
- записывать `egress_interface`, `egress_gateway` (если доступен), `observed_public_ip` (с оговоркой о внешнем сервисе), `policy_applied` и `route_proof` в отчёт;
- если тест пошёл в пользовательский VPN или другой egress — `ROUTE_MISMATCH` / `INVALID`, **не** ложный `OK`;
- если API нет, продолжать проверку независимыми командами ядра/pcap; presence mawg/MagiTrickle не является обязательным.

### Нельзя делать

- Не вызывать через mawg команд переключения VPN-пула ради очередной DPI-стратегии.
- Не создавать отдельную MagiTrickle-группу в рабочем конфиге на каждом тесте; это противоречит требованию не изменять firewall и создаёт race с текущими политиками.
- Не доверять ответу `mawg` «канал работает» как доказательству отсутствия DPI: его probe может идти через VPN.
- Не вызывать `lxd /admin/apply` на работающем пользовательском sing-box для управления тестовыми стратегиями Zator.

## 6. Обязательные проверки совместимости

1. **Без соседних проектов:** Zator + Router Agent + выбранный SOCKS работает автономно.
2. **Проекты установлены, не активны:** фоновая проба не включает их.
3. **mawg активно ротирует VPN:** тест остаётся на заявленном WAN (или сразу становится `INVALID`).
4. **MagiTrickle обновляет DNS/группы:** проверка не меняет пользовательские правила и не принимает false positive.
5. **Рабочий sing-box-lx уже запущен:** отдельный test instance не использует его config/PID/TUN/API, не вызывает reload.
6. **Ресурсный лимит:** на слабом MIPS/128 МБ не возникает OOM или деградации обычного nfqws2.
7. **Сбой тестового процесса:** рабочие VPN/policy/`nfqws2` остаются в состоянии до пробы.
8. **IPv4-only:** DNS AAAA, QUIC/UDP и попытка обхода тестового SOCKS правильно помечаются как unsupported/INVALID, не считаются проверкой стратегии.

## 7. Правило лицензий и зависимостей

Перед переносом конкретного кода прочитать `LICENSE` и notices **в указанном commit SHA** всех проектов и зависимостей. При несовместимости — реализовать отдельный адаптер/протокол без копирования кода. Не использовать `internal/*` из mawg как «официальный SDK»: пакеты Go с `internal/` нельзя импортировать из произвольного стороннего модуля.

Любой mandatory dependency должен иметь:
- способ установки/обновления под целевую Entware ABI;
- minimum version + feature-detection вместо догадок;
- чёткий механизм восстановления после аварии;
- ограничение RAM/CPU и fallback;
- проверяемое разделение production и test процессов.

## 8. Решение Gate G0

После аудита агент заполняет:

| Поле ADR | Что записать |
| --- | --- |
| SHA всех четырёх проектов | Зафиксировать реальные commit SHA/ветку; не оставлять «latest» |
| Целевой Keenetic | модель, KeeneticOS, CPU ABI, Entware, RAM |
| Выбор SOCKS runtime | `sing-box-lx isolated` / `compact SOCKS`, объективная причина |
| Маршрутизация | наблюдаемый test WAN, конфликтующие mark/policy |
| Схема идентичности | PROXY_UID, NFQWS_UID, queue, ct mark, порты, избежание collisions |
| Изоляция процессов | доказательство независимости от Zator/mawg |
| Измерения | RSS/CPU/TCP success, stability, crash recovery |
| Оставшиеся риски | какие тесты не прошли и что блокирует G1 |

**Критерий G0:** выбран исполнимый вариант с измеренной пригодностью на роутере и доказуемым тестовым путём; иначе дальнейший GUI не реализовывать как «рабочий обход DPI».
