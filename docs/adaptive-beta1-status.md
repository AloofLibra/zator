# Adaptive Agent Beta 1 status

Status against `zator_dynamic_agent_beta1_tasks_v1_1.md`. This is an implementation ledger, not a release approval. Missing hardware evidence remains `NOT VERIFIED`.

Internal operator instructions and current limits are in [adaptive-beta1-user-guide.md](adaptive-beta1-user-guide.md); the guide explicitly keeps the feature experimental while mandatory hardware gates remain open.

## Current increment

- FastSearch now treats a timeout, HTTP rejection, or bounded response as a candidate-level inconclusive result and continues only when the router confirms traffic reached the isolated queue. SUCCESS still requires both the isolated queue and matching strategy ACK. Missing route evidence stops the search; 429 and 5xx produce a target cooldown. Results include per-candidate duration, total search duration, and time to first SUCCESS.
- The controller's authoritative result now exposes separate `queue_seen` and `strategy_ack_seen` fields. The Windows agent never supplies these values.
- Watch now persists bounded exact-target DeepSearch cursors in the Windows user's Zator state directory. After the fast phase it resumes one remaining candidate at a time, no more often than every 120 seconds, when no queued router event needs attention. Candidate-set/catalog changes invalidate the cursor; 429 pauses that target for 15 minutes. The local cursor can contain the tested hostname and IP; it is never part of the statistics spool.
- The Windows agent derives a local Googlevideo ranking group for strict `rrN-<suffix>.googlevideo.com` and `rN---sn-<suffix>.googlevideo.com` names. Other hosts retain exact-name keys. RampAudit now prefers less-recently sampled groups when selecting its next exact target; its persisted cursor stores only a hash of the group ID, while proof and exemption identity remains exact host/IP/scope.
- A higher-priority Watch verification now preempts a running low-priority FastSearch/DeepSearch attempt and leaves the urgent event pending for retry. Cancellation is bound to the exact source port plus a per-search random owner token; the CGI verifies both against the live lease before touching its cancel marker. Legacy ownerless 7-field leases remain readable, while new owned leases use an optional 8th field. Completion also requires the matching owner for owned leases.
- The isolated probe config builder and manual media lease path now accept explicit `standard`, `gv_tcp_plain`, `gv_tcp_ramp`, and `gv_tcp_ramp_syndata` treatments for profile 2. Ramp probes load the dedicated Lua implementation and use an exact-target temporary ipset; the probe records whether it changed the SYN window/scale and observed the ACK threshold that opens Ramp. A positive route verdict requires both stages plus the isolated queue and matching strategy ACK. The controller fingerprints the treatment and requires the same treatment at completion; experimental Ramp results are reported but never stored as ordinary applicable rules. FastSearch/DeepSearch/Explore remain standard-only; generic Watch probes remain standard-only, with the separately gated low-priority RampAudit path described below. The default and legacy Supersweep treatment still forcibly omits Ramp. OpenWrt DIRECT and numbered strategy 2 Ramp media paths are hardware-verified; Keenetic Ramp was attempted but did not confirm late ACK/media. Production bypass/offload proof and broader hardware A/B remain outstanding; bounded software pools, explicit exemptions, and isolated comparison are described below.
- A verified DIRECT result can now be stored and looked up as exact strategy sentinel `0`; the API returns it as `winner_kind: DIRECT`, and the Lua selector passes through the exact host/IP/profile/scope without constructing/executing a numbered plan. Manual locks still win.
- The Googlevideo TCP media recipe resolves a short-lived signed URL on the router, binds it to the exact requested Googlevideo hostname and destination IP, and delivers it once through a private lease. The Windows agent performs a pinned HTTP/1.1 Range download capped at 1 MiB and reports bytes, throughput, duration, and a media verdict. Media rules use a separate `googlevideo-tcp` category in the local store and Lua selector, and DeepSearch cursors are recipe-separated. Signed URLs are excluded from logs and statistics. OpenWrt completed one DIRECT Ramp run and a numbered strategy-2 Ramp/plain/plain/Ramp series on the same target, IP, and URL fingerprint; each numbered probe transferred 1 MiB with q65535 and strategy ACK, and both Ramp stages recorded SYN plus late ACK. Numbered strategy 1 remained inconclusive. The series also produced a live exact Ramp exemption; the later control probe verified Ramp through a temporary exact-tuple-excluded copy of that exception file. A valid live revoke sequence (plain media degradation bracketed by Ramp success), Keenetic TCP media, and alternate-route/offload cases remain unverified. OpenWrt profile-5 QUIC media also has one successful paired-flow run documented below.
- The profile-5 Googlevideo QUIC recipe is wired through candidate selection, lease validation, isolated NFQWS argv generation, controller completion checks, and the Windows client. Leases carry `protocol=udp`; the client requires curl HTTP/3 support, uses `--http3-only`, pins the host/IP and UDP source port, and rejects non-H3 transfers. OpenWrt and Keenetic each have one live strategy-18 1 MiB HTTP/3 media success through q65535 with matching Lua ACK. Ordinary same-host HTTP/3 controls advanced production q300 on OpenWrt and the production UDP queue-300 counters on Keenetic while q65535 was absent. Alternate routes/offload, rebuild/crash during QUIC, sustained contention, and both nfqws2 builds remain unverified.
- The Windows agent rejects unsafe media URL characters and fragments before writing the signed URL to its temporary curl config, and starts curl with `-q` so a user curlrc cannot alter the probe. V2 now accepts separate TLS, Googlevideo TCP media, and QUIC dimensions with bounded media bytes/speed/duration; rankings are separated by provider/profile/protocol/recipe/treatment. The Windows opt-in spool uploads only confirmed successful media rows; media failures are not uploaded. The opt-in ranking client keeps separate bounded cache entries and only reorders local candidates. Local/server smoke coverage passes. On the explicitly authorized test host `178.17.48.174`, the upgraded handler passed a real HTTPS QUIC synthetic ingest/replay/conflict check, a profile-5 recipe ranking GET (`200 not_ready`), and a legacy recommendations GET (`200`). Test token and per-test Redis keys were revoked/removed; stats, nginx, and refresh timer are active. Production was not contacted or changed.
- Media probes require curl 8.4+ before requesting a lease: earlier curl versions do not enforce `--max-filesize` while streaming an unknown-length response, so they cannot guarantee the body cap. The version gate and URL/verdict cases are covered in the Windows agent smoke test.
- The WebUI status API now exposes each applicable rule's `treatment_variant=standard`, `evidence=route_verified`, absolute expiry, and remaining TTL seconds. This reflects the controller storage gate: experimental Ramp treatments remain audit evidence and are not saved as ordinary applicable rules.
- The controller now writes an atomic, mode-600, per-probe `status.tsv` with completion/observation timestamps, outcome/reason, recipe/treatment, exact application scope, route/queue/ACK evidence, media metrics, and elapsed seconds. The WebUI status response selects the latest valid summary and displays category, outcome, reason, evidence, and media throughput; it omits host/IP, strategy fingerprints, test IDs, and signed URL hashes. Run-directory garbage collection bounds summary lifetime.
- The paired watcher now sends a bounded, authenticated status snapshot with its current phase, separate `-UploadStatistics` and `-UseSharedRankings` opt-ins, the last search's checked/Fast/Deep candidate counts, outcome, duration, and time-to-first-success, plus sampled Windows CPU/free RAM/all-interface throughput, router load/RAM/active-probe count, and a target-free count of revalidation targets currently cooling down. The router stores only these fields in a mode-600 file under `/tmp`; the API rejects unknown enum values, excess sizes, stale snapshots, and symlinks. The WebUI displays the aggregate values and does not receive the search target or per-target cooldown identities. Windows network throughput is an all-interface host counter, not attributable WAN/probe traffic. Samples are taken for low-priority resource checks, not continuously. When the agent goes offline, the snapshot expires after two minutes.
- Windows Watch persists bounded target-free cumulative revalidation counters in the user's local Zator state: recovery means a suspected-failure search returned a confirmed DIRECT/strategy result; failure means the full catalog reached `all_exhausted`. Inconclusive, rate-limited, cancelled, and infrastructure-stopped checks increment neither. The panel reports those definitions explicitly; these metrics do not claim that later user traffic succeeded after applying a rule.
- The observation queue now distinguishes `active_rule_degraded` from a generic `suspected_failure`: the Lua selector records whether the exact adaptive tuple was selected on that flow, and only two independent failure signals from selected-rule flows create the degraded state. The paired Watch prioritizes it, preempts low-priority work, and performs exact forced revalidation with the same retry/backoff and no-ack behavior as suspected failures. The panel labels it as a possible degradation, not a confirmed user-visible outage. Per-target cooldown state still remains private to the Windows agent and is not yet surfaced as an event state.
- The router rule store now detects semantic A→B→A reassignments for the exact host/IP/profile/protocol/scope tuple. It hashes the tuple, retains only the prior two semantic fingerprints for at most 255 identities, and stores a cumulative aggregate count in the same private file; eviction no longer lowers the displayed total. Identical refreshes and one-way A→B changes do not count. After a tuple is evicted, its earlier fingerprints are unavailable for detecting future reversals; removing the local metrics file clears the aggregate.
- Profile-2 candidate ordering now uses a router-derived, versioned local Googlevideo group key. Only `rrN-<same suffix>` and `rN---sn-<same suffix>` transfer ranking hints; `index`/`index2`, differing `sn` suffixes, unrelated hosts, client scopes, and exact auto-rule application remain separate. Group IDs stay local and only reorder candidates; this does not transfer Ramp exemptions.
- Low-priority Explore now requests a family-diverse local order, interleaving clone, hostfakesplit, multisplit, fake, split, and other strategies instead of exhausting numeric order. Its persisted per-target cursor is bound to the returned candidate-set SHA-256; changes to the catalog, candidates, or ordering reset that cursor safely, while ordinary pacing updates retain it. The server supplies no job dispatch. API ordering and Windows PowerShell 5.1/7 state migration are covered by focused smoke tests.
- AGENT_BETA now records a separate private, bounded (128-row) Googlevideo Ramp target catalog from real profile-2 TLS observations. Rows retain exact host/IP/client scope and a strict local group key; they are deduplicated and evicted oldest-first. The authenticated read-only API exposes only fresh, schema-valid records while AGENT_BETA is active. It reports `ramp_default` only when the installed config enables Ramp and the exact IP is in its configured IPv4 pool; otherwise the target remains pending. API filtering rejects malformed hosts, non-public IPv4, unsupported scopes, stale timestamps, and unknown state/provenance values. The catalog follows observe/pause/clear/disable lifecycle handling.
- The Ramp observation catalog now detects distinct fresh hostnames sharing the same destination IP and client scope, marks those rows `conflict`, and serializes the bounded catalog through a temporary file. The API preserves that state instead of advertising the address as a plain `ramp_default`. This catalog remains observation-only; the separate proof-gated SYN exemption and revocation path is described below.
- Windows Watch has an explicitly requested `-RampAudit` low-priority path. It requires AGENT_BETA, a target classified `ramp_default` or `ramp_exempt`, no urgent/ordinary queued work, idle router probe slot, and available PC/router resource budgets. One isolated treatment is run per cooldown interval, in the order Ramp → plain → plain → Ramp; each stage is pinned to the same candidate number and candidate-set version. Cursor rows are bounded to 128 and store hashed identities, counts, phase, outcome, media URL hash, and the four router result IDs (never the signed URL). The router controller caches one signed media URL privately under `/tmp` for at most 20 minutes per exact host/IP/video ID, and controller results expose only its SHA-256; the transition helper rejects a URL change mid-series. After a verified series, Watch asks the router API to apply an exact IP/scope exemption. The API verifies all four controller results, common URL hash and strategy, media size, current pool membership, fresh observation, absence of shared-IP/DNS conflicts, Ramp enabled, AGENT_BETA, and the explicit LAN consent marker. The runtime Lua callback bypasses only Ramp for new SYNs while the six-hour tmpfs rule is valid; the normal production nfqws2 TLS strategy remains active. Watch schedules a renewal audit after five hours. Expiry, lost consent, reboot, or a conflict restores Ramp for new flows; active connections remain pinned. If the first plain control is degraded for an allowlisted target-path reason, Watch requires a successful Ramp → plain-degraded → Ramp comparison on the same signed URL before revoking the exact exemption; the router API independently verifies route, queue, ACK, target, strategy, and URL hash on all three results. Timeouts, origin failures, and rate limits alone do not revoke.
- Ramp control probes now use a mode-644 temporary exemption file inside that isolated probe run when an exact active exemption matches its host/IP/scope. Only that tuple is removed from the probe copy; the production exemption file and unrelated exemptions are unchanged. Without this, Lua correctly bypassed Ramp during the final Ramp control and the audit could never verify recovery. Covered by `tests/adaptive_controller_ramp_exemption_smoke.sh` and a live OpenWrt strategy-2 Ramp control.
- Suspected failure events for an active exact rule can now request a force-revalidation candidate set that places the active numbered strategy first; the controller removes that rule only after a route-verified failed recheck whose strategy and fingerprint still match the stored rule. A timeout remains `INCONCLUSIVE`, so it cannot enter the removal branch. The existing Lua detector requires two distinct failed connections before emitting `suspected_failure`, and completed event acknowledgement suppresses the tuple for one hour. Retry state now survives agent restarts with bounded backoff (next bullet); multi-agent coordination, explicit stale-rule fallback policy, and trusted activation lifecycle remain open. The candidate API rejects malformed force flags.
- Watch now persists bounded, hashed-target revalidation retry rows in the Windows user state directory. Infrastructure or invalid search results remain unacknowledged and retry after exponential backoff (60 seconds initially, capped at 30 minutes); rate-limited targets wait 15 minutes before retry. Completed searches clear the retry row and acknowledge the router event. This survives Windows-agent restarts without writing host/IP into retry state. Multi-agent coordination and full per-rule lifecycle remain open.
- The authenticated `events` poll and new `lease` request now invoke the existing ownership-checked stale-probe recovery before returning observations or starting another test. A `SIGKILL`ed controller can therefore be cleaned up on the next Watch poll; if the queue PID/process/private Lua/firewall ownership cannot be proven, the API returns 503 and does not continue. The mock API test verifies both call sites and fail-closed behavior; real router crash/reboot recovery remains unverified.
- On Keenetic 3964, the current recovery library copied only to `/tmp` removed three temporary iptables hooks and both temporary chains for a synthetic dead-controller lease, released the temporary probe lock, marked the run failed, and left NFQUEUE 65535 free. The temporary files and rules were verified removed. This covers the queue-free stale-owner case; recovery with a live q65535 owner during an actual controller SIGKILL and router reboot remain unverified.
- Added a distinct `AGENT_BETA` mode across the pairing CLI, LAN-authenticated WebUI action, event/API gates, Windows Watch, controller, and Lua selector. It enables observing and probing while exact locally confirmed rules can apply; the legacy `AUTO` gate is unchanged. Default-scope rules are blocked in ordinary Beta mode. A separate `beta-lan` CLI action or confirmed WebUI action writes a private consent marker before allowing those rules across the LAN; switching back to scoped Beta, pausing, or disabling clears that marker. Mode changes restart zapret2 through WebUI; CLI explains that restart is required. Beta is opt-in and experimental; a complete rollback/fallback policy, media recipes, and full hardware evidence remain outstanding.

## Rollback and compatibility

This increment changes Windows-agent search state/preemption and proof cursor, adds signed media URL cache/hash fields and explicit Ramp treatments to the isolated probe config builder, creates only expiring `/tmp` Ramp exemptions after server-side proof validation and explicit LAN consent, and supports DIRECT sentinel rules in the gated local selector. Reboot or expiry restores Ramp without editing the config or persistent pool. Existing seven-field leases remain supported; new owner-bound cancellation cannot match a legacy lease. Live Ramp SYN/late-ACK behavior, numbered strategy-2 Ramp/plain media comparisons, exact exemption application, and isolated Ramp control with that exemption active are verified on OpenWrt. A valid degraded-plain live revoke remains unverified; the test API correctly rejected the attempted revoke because plain media succeeded. Software revocation and rejection cases are covered by smoke tests.
