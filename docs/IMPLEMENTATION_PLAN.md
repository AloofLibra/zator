# План реализации Zator Desktop Probe

**Назначение:** исполнимый план для coding-агента. Каждый этап разбит на конкретные задачи и завершается проверяемым результатом.  
**Входные данные:** действующий репозиторий `AloofLibra/zator`, установленные zapret2/nfqws2 на Keenetic с Entware, Windows-машина для тестов; соседние проекты `MarkinAlexander/mawg`, `MarkinAlexander/magitrickle` и `MarkinAlexander/sing-box-lx` рассматриваются как **кандидаты для переиспользования**, но не обязательные runtime-зависимости.  
**Границы MVP:** реальный Chromium, TCP/HTTPS/WSS, тестирование DIRECT и существующих стратегий Zator, наблюдаемость пакетов, независимый `nfqws2`, отсутствие изменений firewall при переключении стратегий. UDP/QUIC — после MVP.

## Неподлежащие нарушению инварианты

1. Никогда не останавливать и не перезапускать рабочий `nfqws2` ради проб, не менять рабочие профили/lock-файлы и пользовательские правила маршрутизации.
2. Каждый тест пользуется собственной NFQUEUE, процессом `nfqws2`, отдельными временными файлами и однозначно идентифицированными исходящими соединениями. Значения queue/UID/mark не должны конфликтовать с действующим Supersweep, настройками Zator и маршрутизацией.
3. На Keenetic при `start`, `set_strategy`, `stop`, `get_status` нельзя выполнять `iptables`/`nft`-мутации. Поддержание статических правил допускается **только на этапе установки/события пересборки firewall** через штатный hook и при удалении компонента.
4. Пропажа правил, агента, NFQUEUE, телеметрии либо потеря идентичности соединения превращает результат в `INVALID`/`UNKNOWN`, а не в `OK`/`FAIL` стратегии. Никогда не переходить незаметно на рабочий `nfqws2`.
5. DIRECT идёт тем же маршрутом и через тот же тестовый контур, что и остальные стратегии; меняется только применение DPI-десинхронизации.
6. Один активный тестовый сеанс на роутер в MVP; повторный запуск должен либо вернуть существующую сессию владельца, либо отказать понятной ошибкой.
7. Нет открытого неаутентифицированного SOCKS/HTTP/API на LAN/WAN, нет `StrictHostKeyChecking=no`, нет исполнения переданных клиентом shell-строк.
8. Для MVP не обещать поддержку UDP, QUIC, WebRTC, IPv6 и полное соответствие поведению клиента за NAT.

## Этап 0. Аудит проекта и фиксация архитектуры [БЛОКИРУЮЩИЙ]

**Цель:** проверить текущие контракты и устранить риск построить приложение на неверных предположениях.

- [ ] **0.1.** Прочитать актуальный `AGENTS.md`, `lib/supersweep_probe.sh`, `lib/supersweep_transport.sh`, `lib/supersweep.sh`, `lib/config.sh`, `Entware/000-zapret2.sh`, тесты и `config.default`. Зафиксировать дерево вызовов создания тестовой конфигурации и применения стратегии.
- [ ] **0.2.** Составить таблицу портов, NFQUEUE, UID/GID, FW mark, CONNMARK, цепочек и разрешённых диапазонов, уже используемых Zator/Supersweep. Проверить коллизии с правилами Keenetic, пользовательскими policy routing и текущим маршрутом WAN.
- [ ] **0.3.** Проверить реальные возможности целевого Keenetic: архитектура CPU/ABI, Entware, `nfqws2`, `iptables -m owner`, `CONNMARK`, `NFQUEUE`, `--queue-bypass`, SSH port forwarding (`-L`), доступ к `/proc/net/netfilter/nfnetlink_queue`, наличие средств смены UID и контрольного запуска.
- [ ] **0.4.** Проверить, как и когда вызывается `/opt/etc/ndm/netfilter.d/000-zapret2.sh`: значения `$table`/`$type`, порядок относительно рабочего `restart-fw`, повторные вызовы, поведение после смены WAN и обновления/перезагрузки KeeneticOS.
- [ ] **0.5.** Выбрать безопасные идентификаторы тестового процесса/прокси и queue. **Не закреплять без проверки** старые `65535`, `65533` и `0x08000000`: они уже используются фоновым Supersweep. Добавить функцию обнаружения конфликтов и отказ, а не автоподмену занятого ресурса.
- [ ] **0.6.** Принять и записать ADR: `Electron + WebContentsView`, командный JSON API поверх SSH, локальный SOCKS5 на роутере с выделенным UID, статическая NFQUEUE на Keenetic, поддержка IPv4 TCP в MVP.
- [ ] **0.7.** Описать ограничение метода: удалённый SOCKS устанавливает TCP-соединение из роутера, поэтому TCP fingerprint/маршрут отличаются от LAN→WAN forwarded-соединения. Помечать результаты типом транспорта `router_socks_tcp`.
- [ ] **0.8.** Создать отдельную ветку/пакеты проекта. Сохранить старую логику Supersweep как есть; не смешивать рефакторинг существующей системы с внедрением нового тестировщика.
- [ ] **0.9.** Прочитать текущие README и соответствующие реализации в `MarkinAlexander/mawg`, `MarkinAlexander/magitrickle`, `MarkinAlexander/sing-box-lx`; сверить коммиты/ветки, лицензию, API, версии и поддержку нужной архитектуры. Результат внести в `EXISTING_PROJECT_REUSE.md`.
- [ ] **0.10.** Оценить запуск **отдельного** `sing-box-lx` с минимальным `socks` inbound и `direct` outbound под `PROXY_UID` без TUN/VPN/правил маршрутизации; измерить суммарную RAM/CPU на Keenetic с запущенными рабочими Zator, mawg и MagiTrickle. Сравнить с лёгким SOCKS-сервером.
- [ ] **0.11.** Снять read-only snapshot маршрутизации: таблицы `ip rule/route`, marks, маршруты WAN, установленные MagiTrickle/mawg правила, DNS и действующие туннели. Определить способ доказать, что **тестовый поток выходит к провайдеру напрямую**, а не через рабочий VPN. Без такой проверки результат может быть ложноположительным.
- [ ] **0.12.** Зафиксировать ADR «reuse or not»: `sing-box-lx` — отдельный SOCKS-процесс либо облегчённый fallback; `mawg` — только платформенные/диагностические адаптеры; MagiTrickle — optional read-only discovery. Исключить изменение живых VPN-пулов, DNS-групп и MagiTrickle-групп во время тестов.

**Артефакты:** `docs/desktop-probe/ADR.md`, `docs/desktop-probe/compatibility.md`, сравнительный PoC прокси-движков, snapshot policy routing и заполненный `EXISTING_PROJECT_REUSE.md`.  
**Критерий завершения:** фактическая совместимость **конкретного** Keenetic подтверждена, все идентификаторы и путь трафика согласованы, отсутствует блокирующая коллизия. Если нет SSH forwarding или Netfilter capabilities — остановиться и выбрать альтернативу в ADR.

## Этап 1. PoC реального тестового трафика без GUI [БЛОКИРУЮЩИЙ]

**Цель:** доказать, что браузерное TCP-соединение можно направить в отдельный `nfqws2`, не затронув рабочие потоки.

- [ ] **1.1.** Запустить **выбранный на этапе 0** отдельный SOCKS5 TCP CONNECT сервер. Кандидат A: новый независимый процесс `sing-box-lx`, профиль только `socks` inbound + `direct` outbound, без VPN, TUN и модификации рабочего конфига mawg. Кандидат B: компактный SOCKS (если память/архитектура не позволяют A). Разрешать подключения только на `127.0.0.1:<port>`; в MVP UDP ASSOCIATE отключить. Проверить реальную конфигурацию командой `sing-box check`, не считать пример готовой поставляемой схемой.
- [ ] **1.2.** Запускать прокси **под выделенным непривилегированным UID**, отличным от UID рабочего и тестового `nfqws2`. Если отдельный пользователь/смена UID недоступны — оформить блокер; не классифицировать прокси только по PID (`owner` не работает по PID).
- [ ] **1.3.** Поднять SSH `-L` с ПК к `127.0.0.1:<router-socks-port>`, протестировать SOCKS5 CONNECT и прокси-DNS на роутере. Показать успешный `curl`/браузерный TCP HTTPS через канал.
- [ ] **1.4.** Создать минимальную **статическую** test NFQUEUE-конфигурацию: помечать upstream TCP-сокеты SOCKS по UID, сохранять идентичность соединения через conntrack, доставлять требуемые исходящие и ответные пакеты в тестовую очередь, исключать их из рабочей очереди.
- [ ] **1.5.** Запустить отдельный `nfqws2` с приватной конфигурацией; загрузить рабочий Lua/strategy plan из текущего Zator без обращения к рабочим lock-файлам.
- [ ] **1.6.** Проверить DIRECT и хотя бы одну выбранную стратегию на новой TLS-сессии. Записать pcap/счётчики очереди/лог тестового `nfqws2` и убедиться, что обработано **именно** соединение от выделенного прокси.
- [ ] **1.7.** Одновременно генерировать обычный пользовательский трафик с другого устройства. Проверить: счётчики тестовой очереди не растут от обычных сессий; рабочая очередь не получает тестовые соединения; рабочие файлы и процессы не меняются.
- [ ] **1.8.** Во время одного теста заставить Keenetic пересобрать firewall, затем повторить запрос. Система должна восстановить test rules или отклонить тест как `INVALID`; HTTP-ответ в обход тестовой очереди не может считаться успехом.
- [ ] **1.9.** Проверить тест при остановленном тестовом `nfqws2`, отключении SSH и коллизии UID/queue. Недостаток изоляции — блокер, а не повод сделать fallback на production NFQUEUE.
- [ ] **1.10.** Повторить пробы с одновременно активными `mawg` и MagiTrickle, включая текущую VPN-policy и её перестроение. Зафиксировать фактический выходной интерфейс/IP, DNS-путь и raw fake-пакеты; при выходе тестового трафика через VPN выставить `ROUTE_MISMATCH` / `INVALID`, не объявлять стратегию рабочей.
- [ ] **1.11.** Проверить, что запуск/остановка отдельного `sing-box-lx` (если выбран) не вызывает reload/stop/перезапись конфигурации уже запущенного sing-box-lx или mawg, и что тестовый UID отличается от UID рабочего и тестового nfqws2.

**Артефакты:** `tests/manual/keenetic_probe_poc.md`, пакет минимальных команд воспроизведения, лог и краткое описание packet path.  
**Критерий завершения:** доказана изоляция на физическом роутере, подключение от ПК через SOCKS, работа DIRECT и хотя бы одной стратегии. После этого можно создавать полноценный агент и GUI.

## Этап 2. Постоянная инфраструктура изоляции на роутере

**Цель:** превратить экспериментальные правила в воспроизводимый, идемпотентный компонент Zator.

- [ ] **2.1.** Вынести код статического тестового транспорта в отдельный модуль, например `z2r_lib/desktop_probe_transport.sh`. **Не изменять** семантику существующего `supersweep_transport.sh` без отдельной необходимости.
- [ ] **2.2.** Реализовать `install/reconcile/status/uninstall` со строго собственными цепочками и comment-маркерами. `reconcile` идемпотентен, не делает `flush` чужих цепочек и не удаляет правила рабочего zapret2.
- [ ] **2.3.** Подключить `reconcile` к существующему `Entware/000-zapret2.sh` после восстановления рабочего zapret2/client scope. Фильтровать `$type`, `$table`, не создавать дубли при многократных событиях.
- [ ] **2.4.** Не только вставить test NFQUEUE, но и строго обеспечить **обход рабочей NFQUEUE** для test flow в обе стороны. Отдельно обработать уже маркированные/raw fake-пакеты тестового `nfqws2` и исключить повторный перехват и циклы.
- [ ] **2.5.** Проверить порядок MARK/CONNMARK/NFQUEUE/ACCEPT/RETURN относительно штатных правил и возможных policy routing. Проверить, что добавленная марка не перенаправляет трафик в VPN или на другой WAN.
- [ ] **2.6.** Отделить идемпотентную проверку состояния от восстановительных мутаций: штатный тест делает только `status`, восстановление запускает netfilter hook/установка. Смена стратегии не вызывает `reconcile`.
- [ ] **2.7.** Учитывать пересоздание таблицы *посередине запроса*: generation token/counter, fingerprint правил, correlation с test session. При изменении поколения тест помечается `INVALID` и при необходимости повторяется.
- [ ] **2.8.** При удалении компонента удалять только принадлежащие ему цепочки/правила и hook-вызов. При сбое cleanup оставлять диагностируемое состояние и повторяемое удаление.
- [ ] **2.9.** Подготовить mock-тесты генерации правил, порядка цепочек, коллизий, отсутствия дублирования и недопустимых вызовов iptables во время работы.

**Артефакты:** новый транспортный модуль, обновлённый Keenetic hook, unit/smoke tests.  
**Критерий завершения:** 10 повторных событий firewall не создают дублей; test traffic обрабатывается test NFQUEUE; рабочая функциональность Zator не меняется; приложение может выполнить множество проб без единого изменения firewall.

## Этап 3. Router Agent: управление сессиями, `nfqws2` и прокси

**Цель:** создать небольшое локальное приложение/CLI, которым десктоп управляет по SSH.

- [ ] **3.1.** Выбрать реализации: минимальный бинарник под целевые архитектуры Entware (в том числе MIPS/ARM, если поддерживаются), либо небольшой shell-wrapper поверх `nfqws2` + отдельный SOCKS-бинарник. Предпочесть повторное использование `sing-box-lx` **как отдельного data-plane процесса** только если прошёл PoC по памяти и изоляции; иначе компактный SOCKS. Не требовать Python и постоянного сервиса mawg.
- [ ] **3.2.** Реализовать команды `capabilities`, `start`, `set-strategy`, `status`, `telemetry`, `stop` и машинно-читаемый `--json`. Контракт см. `ARCHITECTURE_AND_PROTOCOL.md`.
- [ ] **3.3.** `start`: валидация профиля/очереди/UID/маркеров, lock сессии, приватный каталог `/tmp/zator-desktop-probe/<session-id>`, сохранение snapshots, запуск proxy и отдельного `nfqws2`. Запускать демоны так, чтобы закрытие SSH не отстреливало дочерние процессы, но с bounded TTL.
- [ ] **3.4.** Перенести и параметризовать подготовку конфигурации из `supersweep_probe_config`: `qnum`, uid, приватные lock-файлы, конфиг установленного Zator. Не зависеть от жёстко заданных `65535` и `62000–62999`.
- [ ] **3.5.** `set-strategy`: принимать только существующий номер стратегии в заданном профиле либо `DIRECT`. Менять только приватный state/lock. Атомарно записывать файл; дождаться применения по механизму Lua или истечению гарантированной границы кеша; вернуть `generation`/`applied_at`.
- [ ] **3.6.** `status`: фактические PID, очереди, proxy listener, текущая стратегия, поколение firewall, здоровье transport, свободная RAM, срок жизни сессии, ошибки Lua. Проверять PID и cmdline, не доверять только pidfile.
- [ ] **3.7.** `telemetry`: счётчики тестовой NFQUEUE и целевых flow, ошибки `nfqws2`, timestamp/generation; при возможности — подтверждение вызова нужной Lua-стратегии. Логи стратегии без секретов и полного содержимого сайтов.
- [ ] **3.8.** `stop`: прекращение новых proxy-connect, остановка **только своих** процессов, ожидание exit, очистка приватных файлов без удаления статического транспорта. Идемпотентное повторение после сбоев.
- [ ] **3.9.** Ввести lease/TTL, heartbeat, lock от параллельных запусков, очистку осиротевших процессов после краша/отключения ПК, а также ручную команду `recover` с идентификацией владельца.
- [ ] **3.10.** Проверить права: минимальные привилегии proxy, root-only доступ к операциям с тестовым `nfqws2`/iptables; привилегированный helper с фиксированным белым списком операций и аргументов, никаких произвольных команд из JSON.
- [ ] **3.11.** Интегрировать установку/обновление/удаление через систему доставки Zator. Если выбран `sing-box-lx`, использовать совместимый уже установленный бинарник **без изменения его глобальной конфигурации**, иначе иметь понятный fallback или отдельную установку с согласием пользователя. При удалении Zator прекратить тестовую сессию, очистить только свои ресурсы; mawg, MagiTrickle и старый Supersweep не сломать.
- [ ] **3.12.** Встроить опциональный read-only `route-inspector`: определения интерфейса, IP выхода, состояния mawg/MagiTrickle, факта policy-based VPN redirect. Не делать их обязательными условиями установки, не копировать целиком чужие `internal` Go packages без проверки лицензий и зависимостей.

**Артефакты:** router CLI/daemon, install/uninstall, описание API и сборки под архитектуры Keenetic.  
**Критерий завершения:** из терминала ПК можно последовательно начать сессию, открыть HTTPS через локально проброшенный SOCKS, выбрать стратегию, получить достоверную телеметрию, остановить всё; работающий `nfqws2` остаётся неизменным.

## Этап 4. Десктопное приложение: транспорт и встроенный браузер

**Цель:** работающий Windows GUI, открывающий реальные сайты через тестовый маршрут.

- [ ] **4.1.** Создать отдельный пакет/репозиторий десктопного приложения: Electron + TypeScript. Собрать инсталлятор Windows и portable сборку для первичных тестов.
- [ ] **4.2.** Реализовать профиль подключения к роутеру: адрес, SSH-порт, логин, ключ/системный ssh-agent, проверка host key, кнопки подключения/диагностики. Не сохранять пароль/ключ в открытом виде.
- [ ] **4.3.** SSH adapter: исполнение allowlisted router-команд с JSON-ответом, запуск/мониторинг SSH `-L` на случайно выбранный свободный **локальный** TCP-порт ПК; проброс только к роутерному loopback SOCKS.
- [ ] **4.4.** Реализовать `WebContentsView` для отображения сайта в окне приложения. Браузерный раздел должен быть изолирован от привилегированного UI (`nodeIntegration=false`, `contextIsolation=true`, `sandbox=true`).
- [ ] **4.5.** Для каждого теста создавать отдельную in-memory `session`/partition, назначать SOCKS5 через `session.setProxy()`, запрещать прямой proxy bypass для целей теста. Не переиспользовать существующие HTTP/2/TLS/TCP соединения между стратегиями; проверять свежесть на уровне соединения.
- [ ] **4.6.** В MVP принудительно отключить QUIC/HTTP3 для тестового контекста (при необходимости на уровне параметров Chromium/сети процесса); явно указывать режим `TCP_ONLY` в UI и отчёте. Проверить, что WebRTC/UDP и разрешение DNS не уходят мимо тестового маршрута; запрещать/маркировать неподдерживаемые функции.
- [ ] **4.7.** Подключить события `webContents` и CDP (`Network`, `Page`): start/finish/fail, HTTP-код, URL, timing, protocol, redirect, TLS/cert errors, WebSocket. Не логировать cookie, Authorization и тела запросов.
- [ ] **4.8.** Создать UI: выбор роутера, URL/набор тестовых сайтов, профиль стратегий, DIRECT, прогресс, live preview, лента запросов, журнал ошибок, таблица стратегий, детали одного результата.

## Этап 5. Тестовый оркестратор стратегий

**Цель:** автоматизировать цикл проверки без порчи результатов и пользовательского трафика.

- [ ] **5.1.** Реализовать конечный автомат: `IDLE → PREPARING → BASELINE → SWITCHING → LOADING → ANALYZING → (RETRY | NEXT) → REPORTING → CLEANUP` с `CANCELLED/ERROR/INVALID`.
- [ ] **5.2.** Для каждого сайта определить профиль Zator по правилам, которые агент получает из актуальной конфигурации; для ручного выбора позволить override. Не определять профиль исключительно по подстроке URL.
- [ ] **5.3.** Перед каждой стратегией получать snapshot `status` и счётчиков. После `set-strategy` дожидаться подтверждённого поколения `applied` и полной остановки старой браузерной сессии.
- [ ] **5.4.** Сначала запускать `DIRECT` через тот же тестовый `nfqws2` и proxy path. Затем проходить **существующие** номера стратегий профиля в выбранном порядке. Не генерировать новые стратегии и не редактировать `config.default`.
- [ ] **5.5.** Для каждой стратегии создавать **новое TCP-соединение**, отдельную browser session, выполнять navigate/load, собирать network events и router telemetry.
- [ ] **5.6.** Разделить ошибки транспорта (`NO_QUEUE`, `PROXY_DOWN`, `SSH_LOST`, `FIREWALL_CHANGED`, `ROUTE_MISMATCH`) и сетевой результат сервиса (`DNS_ERROR`, `TLS_TIMEOUT`, `HTTP_RESPONSE`, `MEDIA_FAILURE`). Первые **не являются FAIL стратегии**.
- [ ] **5.7.** Добавить ограниченное повторение неоднозначных проб и рандомизируемый/повторный контроль эталонной стратегии, чтобы минимизировать влияние времени/нагрузки сервиса.
- [ ] **5.8.** Поддержать manual mode: пользователь видит сайт и подтверждает, что функция работает. Автоматический результат по правилам, ручная оценка и фактическая телеметрия должны храниться раздельно.
- [ ] **5.9.** Реализовать устойчивую отмену и возврат состояния. Нельзя удалять результаты завершённых стратегий и применять найденные варианты в рабочий Zator автоматически.
- [ ] **5.10.** Добавить ручной экспорт стратегии в рекомендованный результат/файл; **никакого автоматического изменения рабочих lock-файлов в MVP**.

**Артефакты:** оркестратор, контракты verdict, тесты переходов и retries.  
**Критерий завершения:** последовательный DIRECT + стратегии выбранного профиля с технически корректным отчётом; все невалидные пробы явно помечены, результаты воспроизводимы.

## Рекомендуемый порядок исполнения и контрольные точки

| Контрольная точка | После этапов | Что должно быть продемонстрировано |
| --- | --- | --- |
| **G0 — feasibility** | 0 | Аудит роутера и трёх соседних проектов, решение по reuse, замеры RAM/CPU, маршрут теста и конфликты подтверждены |
| **G1 — isolated packet path** | 1–2 | SOCKS CONNECT с ПК → собственная NFQUEUE → тестовый `nfqws2`; пересоздание firewall не ломает безопасность |
| **G2 — agent CLI** | 3 | Полный цикл `start → DIRECT → strategy N → telemetry → stop` без GUI |
| **G3 — desktop preview** | 4 | Сайт открывается встроенным Chromium через SSH/SOCKS, сетевые события наблюдаемы |
| **G4 — full TCP sweep** | 5–6 | Чистые соединения для каждой стратегии, достоверная классификация и отчёт |
| **G5 — beta** | 7 | Стабильная установка, regression и failure tests пройдены |
| **G6 — extended transport** | 8 | QUIC/UDP и туннельная архитектура подтверждены отдельно |

**Запрет на параллелизацию:** этапы 0–2 последовательны и блокируют GUI/оркестратор; этап 3 должен стабилизировать контракт до тесной интеграции с этапом 4. После G2 параллельно допустимы UI, сценарии анализа и автотесты.

## Обязательная форма отчёта coding-агента после каждого этапа

1. Что сделано; ссылки на commit/PR и конкретные пути изменённых файлов.
2. Какие команды, unit/smoke/integration тесты реально запущены, их результат и среда.
3. Какие инварианты изоляции проверены физически, какие проверены только mock-ами.
4. Как ведёт себя решение при аварии; что осталось непроверенным.
5. Какие настройки роутера нужны пользователю, какие ограничения обнаружены.
6. Решение контрольной точки: `PASS`, `BLOCKED`, `PARTIAL` с объяснением; к следующей точке не переходить при `BLOCKED`.

## Не делать в MVP

- Не менять/«оптимизировать» рабочий Supersweep в рамках задачи.
- Не считать признаком работы сайта единственный успешный HTTP HEAD или `HTTP 200`.
- Не внедрять TUN/QUIC до того, как стабилен TCP probe.
- Не открывать SOCKS5/API наружу, не отключать проверку SSH host key.
- Не выводить на роутер полноценный Chromium.
- Не делать автоустановку найденной стратегии в рабочие `locked.tsv` без отдельной явно подтверждённой фичи.
- Не притворяться, что proxy-originated TCP полностью идентичен трафику обычного клиентского устройства.
