# Проверка SYN-data для Googlevideo

Опция экспериментальная и выключена по умолчанию. Она включается только при активном `wssize_ramp`; фильтрацию IPv4 TCP/443 по Googlevideo IP и существующий mark-профиль выполняет firewall. Выбранную TLS-стратегию профиля `key=2` во всех сравнениях оставляйте одинаковой.

При включении SYN-data по умолчанию используется `tlsgoogle`, объявленный как `/opt/zator/files/fake/tls_clienthello_www_google_com_2.bin`; генерируемая Lua-опция имеет вид `--lua-desync=z2r_googlevideo_syndata:blob=tlsgoogle`. Можно заменить имя на любой другой уже объявленный `--blob`. Если задать `Z2R_WSSIZE_RAMP_SYN_BLOB=` в `/opt/zapret2/config`, штатный `syndata` вернётся к 16 нулевым байтам. Размер содержимого должен помещаться в один исходящий SYN вместе с IP/TCP заголовками и опциями.

## Подготовка

1. Получите свежую подписанную ссылку на видео YouTube и hostname `*.googlevideo.com` из неё. На клиенте разрешите hostname в IPv4 и задайте адрес для фильтра захвата:

   ```sh
   HOST='rr2---sn-....googlevideo.com'
   IP="$(getent ahostsv4 "$HOST" | awk 'NR==1 {print $1}')"
   printf 'host=%s ip=%s\n' "$HOST" "$IP"
   ```

2. На тестовом OpenWrt/Keenetic укажите WAN-интерфейс, через который уходит этот адрес, и начните захват **на WAN**. На OpenWrt интерфейс можно найти через `ip route get "$IP"`; для маркированного маршрута при необходимости укажите интерфейс вручную.

   ```sh
   WAN_IF='pppoe-wan'
   tcpdump -ni "$WAN_IF" -s 0 -tttt -S -vvv -XX "host $IP and tcp port 443"
   ```

   У SYN-data в выводе будут TCP-флаг `S`, TCP Window и 16 нулевых байт после TCP-заголовка. `-S` показывает абсолютные sequence/ack numbers. Захват одновременно покажет SYN+ACK, TLS-записи и последующий поток. Не запускайте параллельно другие соединения к этому адресу.

3. На клиенте выполните один и тот же большой Range-запрос для каждой конфигурации. Не публикуйте подписанную ссылку: она содержит временный токен.

   ```sh
   URL='вставьте подписанную ссылку локально'
   curl -L --fail --retry 2 --connect-timeout 10 --max-time 180 \
     --range 0-104857599 -o /dev/null "$URL"
   ```

   Записывайте результат curl, время, полученный объём и наблюдаемые Window/Window Scale. Повторите каждый вариант несколько раз на одном и том же URL/IP; затем обновите ссылку, если она истекла.

## Сравниваемые варианты

В CLI откройте меню `wssize_ramp` (пункт 7 расширенных настроек) или настройку Ramp в WebUI. После каждого изменения дождитесь штатного перезапуска zapret2.

1. **Обычный TCP:** Ramp выключен. SYN-data при выключенном Ramp автоматически отключена. Существующий профиль `key=2` и его TLS-lock остаются как есть.
2. **Ramp:** включён Ramp, SYN-data выключена. Повторите отдельно в режимах Full и Lite.
3. **Ramp + SYN-data:** Ramp включён, выбрана та же Full/Lite конфигурация, включён переключатель «SYN-data для Googlevideo (экспериментально)».
4. **Ramp + SYN-data + другая TLS-стратегия:** оставьте Ramp/SYN-data включёнными и смените только действующий lock `key=2` штатным меню стратегий. Не добавляйте новую стратегию и не меняйте RST Guard.

Проверьте по захвату, что в варианте 1 и 2 клиентский SYN без payload; в вариантах 3 и 4 для первого SYN появился payload, а клиентский TCP handshake, TLS handshake и Range-загрузка завершаются. Посмотрите, что ретрансляции SYN не вызывают повторных инъекций, SYN+ACK подтверждает ожидаемую последовательность, а входящие RST продолжают обрабатываться штатно.

Если сервер принимает TCP Fast Open, он может обработать данные в SYN иначе. В частности, необычный ACK может нарушить handshake клиента. Функция не сдвигает sequence numbers автоматически; при сбое выключите SYN-data и повторите тест.

## Реальный тест на OpenWrt

На тестовом OpenWrt 25.12.4/aarch64 проверены запросы к `rr2---sn-h5gtov-n8vl.googlevideo.com` (`188.244.8.77`). Обычный TCP, Full Ramp без SYN-data, Full с 16 нулевыми байтами и Lite с 16 нулевыми байтами завершили TLS и получили HTTP 404 от корневого URL. Захват подтвердил Ramp Window=1/Scale=1, а SYN-data — payload длиной 16. Затем `tlsgoogle` (652 байта) также был виден в SYN; handshake завершился успешно и сервер вернул HTTP 404.

Там же `google_www` (681 байт, TLS ClientHello) действительно появился в TCP SYN, но запрос завершился timeout за 6 секунд. Этот blob нельзя считать рабочим для SYN-data на Googlevideo; проверяйте выбранный payload на целевом сервере и оставляйте режим выключенным при проблемах.
