# Адаптивная авторотация: контракт v1

Статус: частичный прототип PR-A–G. Наблюдение, одиночный TEST_ONLY probe, Windows watcher для FastSearch, локальное ранжирование, opt-in медленное исследование и начальная WebUI-панель управления подключены к Bash runtime. Windows-агент имеет явные раздельные opt-in для отправки агрегатов (`-UploadStatistics`) и чтения общих рейтингов (`-UseSharedRankings`). Server V2, установщик и клиентский GET precomputed rankings реализованы; FastSearch использует рейтинги только для порядка кандидатов после локальных подтверждений и всегда перепроверяет точной локальной пробой. Без `-UseSharedRankings` агент не запрашивает локальный ISP-провайдер и не обращается к серверу рейтингов. V2 установлен и проверен на отдельной test VM; production stats-хост не менялся. Живая HTTPS-проверка и Redis-нагрузка на test VM описаны в `adaptive-stats-v2.md`; они не являются приёмкой production-хоста. На OpenWrt и Keenetic подтверждён парный LAN-поток через test queue 65535 и обычный HTTPS к тому же hostname через production queue 300; подробности и ограничения зафиксированы в baseline-файлах. Аппаратная приёмка всё ещё неполная. Production auto-apply выключен. Это протокол Bash Zator, не ZatorGO.

## Границы v1

- MVP: IPv4, TCP/443, TLS + ограниченная HTTP-проверка; никаких автоматических изменений production-локов до локальной валидации.
- Тест считается допустимым только при доказанном прохождении отдельной test NFQUEUE и подтверждении выбранной стратегии. Нет доказательства маршрута/очереди — `INCONCLUSIVE`.
- Исторический номер `strategy=N` не является ID. Сопоставление кандидата привязано к fingerprint стратегии и версии каталога.
- Ручные локи и исключения имеют приоритет; OFF не наблюдает, не тестирует и не применяет.
- Клиентский агент выполняет только ограниченную локально разрешённую пробу; сервер не передаёт произвольные URL или команды.

## Модель результата

Один JSON-объект на тест, UTF-8, версия задаётся `schema_version`:

```json
{
  "schema_version": 1,
  "test_id": "opaque-unique-id",
  "route_verified": false,
  "transport": "UNKNOWN",
  "application": "NOT_TESTED",
  "overall": "INCONCLUSIVE",
  "reason": "route_unverified",
  "observed_at": 0,
  "target": {
    "hostname": "example.org",
    "destination_ip": "192.0.2.1",
    "ip_family": "ipv4",
    "protocol": "tcp",
    "port": 443,
    "profile_id": 1,
    "scope": "default"
  },
  "strategy": {
    "fingerprint": "sha256:<hex>",
    "local_number": 1,
    "catalog_version": "opaque-version"
  },
  "recipe_id": "tls-http1-v1",
  "client_profile": "curl-windows-v1"
}
```

Допустимые значения:

- `transport`: `OK`, `FAIL`, `UNKNOWN`.
- `application`: `OK`, `FAIL`, `NOT_TESTED`, `UNKNOWN`.
- `overall`: `SUCCESS`, `FAIL`, `INCONCLUSIVE`.
- `reason`: стабильный машинный код, например `route_unverified`, `queue_unavailable`, `strategy_unconfirmed`, `target_unavailable`, `timeout`, `http_rejected`, `probe_ok`, `cancelled`, `expired`. Не использовать свободный текст как основание для автоматики.

`SUCCESS` требует `route_verified=true`, `transport=OK` и `application=OK`. `FAIL` допустим только при подтверждённых маршруте/стратегии и корректно выполненном рецепте; неопределённая причина всегда `INCONCLUSIVE`. Повторный `test_id` идемпотентен и не должен повторно менять состояние.

## Состояния задания

`DISCOVERED → QUEUED → LEASED → PROBING → VERIFIED → CANDIDATE → APPLIED|REJECTED`.

Терминальные альтернативы: `CANCELLED`, `EXPIRED`, `INCONCLUSIVE`. Переходы и применение должны быть сериализованы одним локальным владельцем; чужой процесс/очередь не останавливать.

## Версионирование и совместимость

- Неизвестная `schema_version`, enum или обязательное поле отклоняет запись без изменения локов.
- Неизвестные дополнительные поля игнорируются только в пределах лимита размера запроса.
- На сервер передаются агрегированные результаты без URL, IP клиента и истории посещений. Старые endpoints рекомендаций и Supersweep остаются без изменений.
- Протокол API/агента и серверный контракт должны получить отдельные схемы и smoke-тесты до реализации соответствующих этапов; этот документ не объявляет их реализованными.

- Изолированный probe и жизненный цикл: `lib/supersweep_probe.sh`, `lib/supersweep.sh`.
- Транспорт, mark и восстановление Keenetic: `lib/supersweep_transport.sh`, `Entware/000-zapret2.sh`.

## Не утверждается этим контрактом

LAN→NFQUEUE изоляция, Windows source-port binding, соответствие реально применённой стратегии, firewall cleanup на OpenWrt/Keenetic, нагрузочные бюджеты и корректность реальных сетевых вердиктов требуют отдельных интеграционных измерений. До их прохождения AUTO недоступен.

Локальный transport helper поддерживает iptables и native nftables. Он отказывает, если queue 65535 уже занята/упоминается в firewall-правилах или если владелец очереди не совпадает с ожидаемым `nfqws2` PID, не использует UID 65533 и приватный `probe/locked.lua`. nftables-вариант цепляется к штатным `postnat_hook`/`prenat_hook`, чтобы обработать обе стороны до production NFQUEUE. Это защитные precondition-проверки, а не доказательство реальной доставки пакетов или изоляции production-трафика.

## Windows agent prototype status

`tools/adaptive-agent.ps1` is the client-side prototype for the v1 recipe. It expects authenticated `application/x-www-form-urlencoded` POSTs to `/cgi-bin/adaptive.cgi`: a lease request followed by a flattened result submission. Before requesting a lease, the Windows client temporarily binds a local listener to find a currently available port in `62000–62999`, then asks the router to lease that exact port. The server validates it and binds the lease to the router-observed source IPv4 address, one IPv4 destination, TCP/443, a short expiry, profile, client scope, and strategy fingerprint. Older clients may omit `source_port` and retain server-side random allocation. The client pins `curl.exe` to that tuple, disables proxies and redirects, uses HTTP/1.1 with certificate validation, requests a bounded byte range, and enforces a hard 64 KiB response cap. Servers that ignore Range remain inconclusive when the body exceeds the cap. It reports only the machine-readable observation; the router derives `route_verified` and the final `overall` verdict from its own queue evidence. `-ListEvents` reads the observation queue; `-EventIndex N -StrategyNumber S` explicitly selects one listed event for a single probe and carries that event's profile and scope into the lease. `-FastSearch` tries the isolated `DIRECT` baseline, then asks the router for up to ten local profile candidates and tests them one at a time, with a 15-second default pause; it stops at the first route-verified HTTP success. The router first checks for an exact local success with a current runtime stamp and returns it without a probe. Otherwise, currently valid successes for distinct tuples in the same profile, client scope, runtime stamp, and strategy catalog are counted locally and ranked first. Ranked candidates are deduplicated by semantic fingerprint over selected strategy arguments, blob contents, isolated Lua module contents, profile, and nfqws2 version; file paths are excluded and generated probe `locked.lua` resolves to its installed source; responses expose both the full numeric profile size and the unique candidate count for pagination, plus a candidate-set version that every ranked continuation page must echo; a stale catalog is rejected instead of silently changing the deep-search order. The opt-in exploration order keeps numeric slots for eventual catalog coverage. Conflicting catalog versions are ignored. When `-UseSharedRankings` is explicitly set, FastSearch may fetch precomputed provider/profile/TLS rankings from V2; without it there is no provider identity lookup or ranking request. Its cache uses 10–30 minute jitter and bounded stale fallback. At most ten validated fingerprints reach the router, where they reorder matching local strategies only after local confirmations. Malformed or unavailable rankings fall back to local ordering, and every winner still needs an exact local probe. The agent reports `fast_candidates_exhausted` when a profile has more strategies than the fast phase covered and includes `search_stop_reason` when a probe or continuation-page error interrupts the search. Profiles with an explicit lock or disable are rejected, candidates never write ordinary profile locks, and only a successful exact tuple can enter the adaptive rule store. `-Watch` adds a client-assisted asynchronous trigger while the Windows agent remains running; router-side scheduling, recommendation-driven failure detection, broader strategy-family ranking, persistent exploration scheduling, and measured CDN pacing remain unimplemented; the V2 fingerprint ranking is an advisory FastSearch input only. Example: `powershell -File .\tools/adaptive-agent.ps1 -Router http://192.168.1.1 -Token <pairing-token> -EventIndex 1 -FastSearch`.

The authenticated Bash CGI and single-probe controller are implemented as a disabled-by-default prototype. Pairing is explicit via `tools/adaptive-pair.sh`; the CGI accepts LAN IPv4 callers only, validates the bearer token and bounded form schema, and the controller derives the final verdict from NFQUEUE sequence movement plus a Lua ACK for the selected host/profile/strategy/scope. The `candidates` action reads the local profile count and refuses profiles with a manual lock or disable. `tests/adaptive_api_smoke.sh` covers authorization, bounded local candidate lists, lease issuance, completion, idempotency, conflicts, and private-target rejection.

OpenWrt 25.12.4 hardware acceptance on 2026-11-21 verified one forwarded LAN IPv4 TCP/443 tuple through nftables: a test request to `www.google.com` was acknowledged by the isolated nfqws2 on queue 65535, while an ordinary request to the same hostname and destination reached production queue 300. Both a numbered strategy and the `DIRECT` sentinel returned `route_verified=true`; the small `/robots.txt` response also produced `SUCCESS`. The test used a temporary `/tmp` runtime root and temporary trace table, then confirmed queue 65535, adaptive nft rules, the shared mutex, and the temporary files were removed; production nfqws2 PID and queue 300 remained. This validates only this OpenWrt topology and selected target. The homepage response exceeded the client's 64 KiB cap, so the exact Windows-agent root-URL recipe was not accepted as an application success in this hardware run.

Keenetic 3964 / Entware (`iptables` 1.4.21) hardware acceptance passed on 2026-11-21 after two fixes in the iptables transport. A fixed test mark collided with active Keenetic policy marks, so the helper now chooses a bit not present in current firewall mark assignments. The original-direction hook now runs at the end of `FORWARD`, after NDM marks, MSS clamping, and the other mangle rules; the exact reply-direction hook runs before the production reply queue. This lets normal forwarding and source NAT run while keeping the test tuple out of production queue 300. A test request from Windows to `www.google.com` pinned to `142.251.155.119:443` returned HTTP 200 with 12,510 bytes; the controller returned `route_verified=true`, `transport=OK`, `application=OK`, `overall=SUCCESS`, and the private Lua ACK confirmed strategy 3 on queue 65535. The adaptive chain counters showed six original and six reply packets traversing the test queue. A separate ordinary HTTPS request to the same hostname and destination, using another source port, also returned HTTP 200; the production TCP NFQUEUE rule counter increased by six packets on queue 300. The tests used only a temporary `/tmp` runtime, rules, and captures. Cleanup confirmed the test queue, adaptive rules, shared lock, tcpdump process, and staged files were removed; production nfqws2 PID 30998 and queue 300 remained.

Other OpenWrt builds, alternate routing/VPN/offload paths, load/resource behavior, and Windows-agent-to-CGI end-to-end behavior remain unverified. On OpenWrt 25.12.4 an active test lease survived `fw4 reload`: the pinned `www.google.com` request (`192.168.10.117:62028 → 142.251.155.119:443`) returned HTTP 200 with 12,510 bytes; q65535's sequence counter rose to 56 during reload and 66 by completion, and the private Lua ACK matched the lease. The controller returned `SUCCESS` with `route_verified=true`; cleanup removed q65535, the adaptive chain, state record, and shared lock. A subsequent ordinary HTTPS request to the same hostname/IP (`192.168.10.117:62029`) returned HTTP 200 while production queue 300 advanced from sequence 100251 to 100275; q65535 was not registered. All staged files and temporary transport state under `/tmp` were removed. The controller's reconcile now excludes its own mark assignments from mark selection and checks the 0600 state with `find -perm 600`, since this OpenWrt has no `stat` command. Partial nft state remains fail-closed and is covered by `tests/adaptive_lan_nft_reconcile_smoke.sh`. Other platforms, alternate routing/VPN/offload paths, and sustained resource limits still need acceptance. AUTO remains unavailable until those gates pass.

Controller cleanup now keeps the shared Supersweep/probe mutex held until its own test `nfqws2` process has exited. Firewall cleanup still happens first while the queue owner is alive; on a firewall cleanup failure, the controller exits while retaining the mutex and probe. This closes a lock-release window in which a second probe could start while queue 65535 remained registered to the previous owner. `SIGKILL` cannot run the cleanup trap. `disable` and `pause` attempt stale recovery only when the recorded controller is dead and the unique incomplete run and its lease can be identified; recovery stops a queue owner only when its argv names that run's private `locked.lua`, then removes the tagged transport rules. Unknown queue owners and ambiguous state fail closed. Controller SIGKILL recovery has now been exercised on OpenWrt through `pause`; reboot/power loss and automatic recovery without a cleanup trigger remain unverified. `tests/adaptive_controller_cleanup_smoke.sh` still covers normal cleanup ordering; recovery safety has separate mocked and live evidence.

The root CLI supports `adaptive-pair.sh status|doctor|create|rotate|observe|test-only|pause|events|clear-events|disable`; the main menu exposes the same operations under item 24 and restarts a running zapret2 after mode transitions. Pairing tokens expire after 30 days; `status` and `doctor` report an expired token, and `rotate` revokes it and prints a replacement. Tokens created by an earlier prototype without expiry metadata must be rotated before API use. The authenticated CGI rejects missing, malformed, or expired token metadata before processing the request. `doctor` performs read-only local prerequisite checks and always reports AUTO unavailable pending Windows-agent/API end-to-end, firewall rebuild/crash recovery, alternate route/offload, and load/resource acceptance. `status` reports pairing, current mode, probe/cleanup counts, queue 65535 ownership, stored-rule count, and event count without exposing host/IP/test IDs; automatic strategy application is explicitly reported disabled. The WebUI also shows the last authenticated Windows watcher heartbeat (online for 90 seconds); the runtime stores only a timestamp, not the client address. `TEST_ONLY` is required to issue a probe lease; `OFF` and `OBSERVE` reject it. `disable` revokes pairing, clears adaptive rules, and waits for active probe cleanup. Pairing and mode behavior are covered by `tests/adaptive_pair_smoke.sh` and `tests/adaptive_api_smoke.sh`.

The Windows probe classifier treats an HTTP response as transport success but only a 2xx response with a non-empty complete body as application success. Redirects, 4xx/5xx, empty 2xx bodies, oversized bodies, and timeouts cannot produce a one-shot `FAIL`; they remain unknown/inconclusive. HTTP 429 maps to `rate_limited` and stops FastSearch; HTTP 5xx maps to `server_busy` and also stops the candidate loop. The mapping lives in `tools/adaptive-agent-verdict.ps1` and is covered by `tests/adaptive_agent_verdict_smoke.ps1`.

Confirmed `SUCCESS` probes are written to the bounded, atomic tmpfs store `rules.tsv` by `lib/adaptive_rules.sh`. Rows bind exact hostname, IPv4, profile, application protocol (`tls`), scope, strategy fingerprint, catalog version, a runtime stamp, and expiry; the lease remains TCP/443. The runtime stamp covers config, nfqws2 binary, lock/override files, loaded Lua modules, Bash catalog/controller inputs, and unique declared blob and Lua-init files using mtime and size. Strategy fingerprints hash the isolated probe Lua modules and declared blob contents while excluding absolute paths; the generated private `locked.lua` is normalized to its installed source module. The Lua module has an exact-tuple parser/lookup with conflict, stamp, and TTL rejection. Production selection requires both `Z2R_ADAPTIVE_RULES_APPLY=1` and runtime mode `AUTO`; `TEST_ONLY` never applies a stored result even if a stale daemon environment retains the variable. No CLI path enables `AUTO`: it remains unavailable until the isolation, semantic catalog, and operational gates pass. The stamp is a stale-data guard, not a cryptographic semantic catalog. Runtime rules and snapshots are mode 0600 and owned by `WS_USER`, so the unprivileged nfqws Lua process can read them. Successful updates schedule a coalesced snapshot to `$ZATOR_ROOT/extra_strats/cache/adaptive/rules.tsv`, normally after 60 seconds and no more than once per five minutes; the Lua loader uses it only when the tmpfs store is absent. The rule snapshot is part of regular backup/restore; the pairing token and mode are deliberately excluded. Service start/restart clears tmpfs but retains the snapshot for stamp-checked recovery; configuration changes and explicit disable remove both copies and advance a generation marker. Power-loss and router flash-wear behavior still need hardware validation.

The first observation path is opt-in via `tools/adaptive-pair.sh observe`; it creates a private `events.tsv` owned by `WS_USER` and sets mode `OBSERVE`. `locked.lua` records one bounded `seen` event per exact host/IP/profile/protocol/scope tuple, keeping a rolling ring of the latest 128 tuples, only for host-known IPv4 TCP/443 TLS connections with no explicit lock or exact adaptive rule. Records contain host, destination IP, profile, protocol, scope, and timestamp only; the collector does not launch subprocesses or change strategy selection. The existing TCP failure detector can promote an observed tuple to `suspected_failure` after failure signals on two distinct connections. This is a prioritization hint for a local `TEST_ONLY` probe, not proof of blocking: it never records a result or changes a strategy by itself. The failure count is process-local and resets on service restart. Queue controls are `pause`, `events`, and `clear-events`. `pause` switches to `OFF`, cancels active probes, and waits for cleanup; `disable` also revokes pairing and clears adaptive state. zapret2 removal runs the same cleanup and refuses to delete runtime files if an isolated probe has not cleaned up. A service restart reloads the mode. The authenticated LAN-only `adaptive.cgi` API exposes a bounded `events` action for the paired agent; on Windows, `tools/adaptive-agent.ps1 -Router http://<router> -Token <token> -ListEvents` reads at most 128 recent validated observations. Active probes require `TEST_ONLY` mode (`tools/adaptive-pair.sh test-only`) and a validated hostname, destination IPv4, profile, and strategy; the watcher takes these from an observed event. `OFF` rejects new leases. DNS hostname/IP TTL attribution remains pending. The WebUI shows sanitized observations and active exact rules (hostname/IP/profile/scope, strategy number, expiry), and permits resetting one exact adaptive rule without restarting zapret2. Pairing-token creation and rotation remain CLI-only.

Any `config_set_var`, application of a new `config.default`, or zapret2 start/restart clears the tmpfs rules. This prevents rules from surviving the configuration and service lifecycle while the full semantic catalog validator is pending; cleanup is deliberately conservative.

## Background observation pilot

The paired Windows agent can now run `tools/adaptive-agent.ps1 -Router http://<router> -Token <token> -Watch`. It polls the authenticated event endpoint every 30 seconds by default (configurable from 10 to 300 seconds), and in TEST_ONLY mode starts at most one FastSearch per poll cycle for an unprocessed observation. It uses the event's explicit hostname, destination IPv4, profile, and scope rather than a queue index. It runs searches serially, so the browser request that caused discovery never waits for candidate probing. OBSERVE only polls; OFF and a stopped agent perform no probes or router traffic changes. TEST_ONLY also collects observations when zapret2 starts in that mode. Ordinary FastSearch deduplication is in memory and lasts only while the watcher process remains alive; the router keeps a rolling ring of the latest 128 distinct tuples in its private runtime queue. This is a client-assisted foreground scheduler, not a router-side daemon: persisted fast-search jobs, DNS attribution/refresh, rate-limit backoff across targets, and automatic rule application are still pending. Example: `powershell -File .\tools\adaptive-agent.ps1 -Router http://192.168.1.1 -Token <pairing-token> -Watch`.

Optional low-priority local exploration is available with `-Watch -Explore`. It requires TEST_ONLY mode and consumes only observed IPv4/TCP/TLS tuples; it does not invent targets or contact a server. The agent checks at most one numbered strategy every 120 seconds by default (configurable from 120 to 3600), adds up to 30 seconds of persisted per-user jitter (configurable), follows a stable numeric sequence for eventual local coverage, and stores only a SHA-256 tuple key, cursor, strategy count, pacing timestamp, and jitter in the per-user Windows state file. Before each passive exploration it requires Windows CPU/network counters to be available and below configurable limits (defaults: CPU under 70%, combined adapter throughput under 1 MiB/s), plus router load below 0.8 per core, at least 32 MiB available memory, and no other active adaptive probe. These router defaults can be adjusted with `-ExploreMaxRouterLoadPerCore` and `-ExploreMinRouterMemoryMiB`; missing counters fail closed. If `needs_verify` arrives during an exploration, the watcher asks the router to cancel only active leases owned by that client's observed LAN IP, waits for probe cleanup, then handles the urgent request on the next loop. The cursor advances before a probe, so restarting the agent cannot immediately repeat the same attempt. Collaborative upload is available only through the separate explicit V2 opt-in described in `adaptive-stats-v2.md`; shared ranking download is separately disabled unless `-UseSharedRankings` is explicitly set. Remote per-client queues remain unimplemented.

An operator can opt into a bounded local deep pass with `-FastSearch -DeepSearch`; the agent tests up to 20 additional local strategy numbers by default (`-DeepSearchMaxCandidates` allows 1–100), one at a time with the same inter-probe pause. The router API pages candidate numbers in batches of at most ten and validates the offset against the current profile count. The pass stops on the first SUCCESS, any inconclusive verdict, or a rate-limit/server-busy response. If strategies remain after the configured budget, the result reports `deep_candidates_exhausted`; it never changes ordinary profile locks.

FastSearch now tries an isolated `DIRECT` baseline (local strategy sentinel 0) before numbered candidates. The private test lock makes `circular_locked` pass the flow without desync, while the separate queue counter and Lua ACK still have to verify the test path. A direct success is reported as `winner_kind=DIRECT` and never stored as a numbered adaptive rule. If direct fails definitively, numbered strategies are tried after the configured inter-probe pause; an inconclusive direct probe stops the search.

The WebUI can enqueue an observation from the last 24 hours for explicit verification. These `needs_verify` requests are kept separately from passive events, capped at 32, expire after 30 minutes, and have a five-minute cooldown per exact tuple. The paired Windows watcher prioritizes manual requests and acknowledges each after the probe finishes, including inconclusive runs. Completed passive tuples are recorded in a separate bounded tmpfs cooldown store for one hour, so restarting the watcher does not immediately replay them. The queue and cooldown store are cleared by `clear-events` and `disable`; TEST_ONLY is required to create or process requests.

Each locally confirmed exact adaptive rule expires after 15 minutes. A new successful local probe is required to refresh it.
