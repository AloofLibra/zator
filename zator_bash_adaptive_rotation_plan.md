# Zator (Bash): план новой адаптивной авторотации

**Статус:** проект архитектуры и план реализации; **целевая база — `AloofLibra/zator`, ветка `zator`**, не ZatorGO.  
**Цель:** подбирать и применять стратегии для реально используемых ресурсов, когда DPI меняет правила по домену/адресу/времени, без ошибочных решений из пассивного анализа трафика, без вмешательства тестов в пользовательские соединения и без перегрузки роутера/центрального сервера.  
**Ограничения:** OpenWrt, Keenetic/Entware и другие поддерживаемые Bash Zator платформы; слабые роутеры; центральный сервер 1 vCPU / 2 ГБ RAM; Windows-клиент для первого прототипа; отсутствие ZatorGO в эксплуатации.

## 0. Фиксируем архитектурные решения

1. **Bash Zator — контроллер.** На роутере остаются обнаружение востребованных ресурсов, локальная очередь, правила, управляющий API, тестовый `nfqws2`, применение результатов и деградация без сервера.
2. **Агент ПК — только исполнитель активных проб.** Первая реализация: небольшая Windows-утилита на базе `curl.exe` / PowerShell либо отдельный независимый клиентский бинарник; **это не переход Zator на Go**. Не хранит рабочую конфигурацию маршрутизатора, не редактирует рабочие локи.
3. **Тестовый путь изолирован.** LAN-пакеты агента через отдельную NFQUEUE и отдельный `nfqws2`. Продуктовые правила и основной процесс не меняются при каждом тесте. При сбое изоляции результаты тестов недействительны.
4. **Два контура:** быстрый подбор для актуальной потребности пользователя и медленное исследование для пополнения/освежения статистики. У медленного — самый низкий приоритет.
5. **Redis — агрегатор и рекомендатель, не оркестратор каждого клиента.** Никаких per-client задач, постоянных соединений, пересчёта сырых Supersweep на каждый запрос, хранения каждого посещённого домена.
6. **Локальная валидация обязательна.** Глобальный топ-10 — приоритет тестирования, а не право автоматически назначить стратегию без проверки.
7. **Все автоматические изменения обратимы.** Ручные локи приоритетнее авто, результаты с TTL; старый режим и вручную выставленные стратегии остаются рабочим fallback.
8. **Новая система включается отдельно.** Существующие Supersweep, `locked.tsv`, ручной режим и телеметрия продолжают работать без новой функции.

**Не цели v1:** 100% распознавание доменов при ECH/DoH; замена браузера агентом; точный анализ содержимого HTTPS; управление VPS со всех WAN; гарантированная актуальность статистики по каждому IP; автоматическая поддержка всех игровых UDP-протоколов.

## 2. Целевая схема данных и поведения

### 2.1. Ключ измерения и назначения

Локальный пробный контекст:

```
scope / source_device
hostname (точное нормализованное имя, если видно)
destination_IP
IP_family (v4/v6)
transport (TCP/UDP)
application_probe (TLS/H1/H2/QUIC/googlevideo-media/...)
profile_id
strategy_fingerprint + local_strategy_number
test_recipe_id + client_profile + observed_at
```

**Важно:** не создавать полный декартов продукт параметров ни в Redis, ни на роутере. Локально храним наиболее востребованные и свежие комбинации; глобально — агрегаты по провайдеру/категории/протоколу и ограниченному набору горячих CDN-групп. Не смешиваем TLS и QUIC, clone/classic, разные blob и несовместимые версии стратегий. В MVP лучше IPv4 + TCP TLS; остальное отдельными этапами.

### 2.2. Иерархия применения

Упрощённая логика для нового соединения:

1. Существующие исключения и явные запреты обработки (`netrogat`, профильный gate) сохраняют приоритет.
2. Явные ручные локи для домена и/или клиента/профиля — приоритетнее любой автоматики. **Точный порядок «ручной домен vs ручной профиль» сохранять согласно текущей семантике**; покрыть тестами.
3. Подтверждённое живое авто-правило exact host + destination IP + protocol + scope.
4. Подтверждённое авто-правило exact host + protocol + scope (только если не противоречит IP-специфике).
5. Осторожный fallback для группы CDN / профиля — при достаточном количестве независимых подтверждений.
6. Старый рабочий профиль / сохранённый manual lock / простой fallback. При неопределённости **не применять случайную стратегию**.
7. `DIRECT` — проверяемый вариант без desync, не воспринимать как очередной номер N без проверки соответствия `nfqws2`.

Авто-правила находятся **в отдельном файле**, например `/tmp/z2r-adaptive/rules.tsv`; в `locked.tsv` автоматические события не записывать. Для восстановления — компактный отложенный снимок под `$ZATOR_ROOT/extra_strats/cache/adaptive/`. Писать tmp+rename; TTL проверять локально; ограничить число правил. На новое соединение выбранную стратегию фиксировать: изменение правил во время TCP/QUIC-сеанса не меняет стратегию посреди обмена.

### 2.3. Вердикты

**Не смешивать**: был ли тест реально проведён через тестовую очередь, прошёл ли транспорт, и был ли успешным прикладной сценарий.

```
route_verified: true/false
transport: OK / FAIL / UNKNOWN
application: OK / FAIL / NOT_TESTED / UNKNOWN
overall: SUCCESS / FAIL / INCONCLUSIVE
reason: enum
```

- `SUCCESS`: тестовая очередь подтверждена, целевой транспорт и необходимый прикладной сценарий завершились успешно.
- `FAIL`: тестовая очередь и рецепт подтверждены, имеются повторяемые признаки недоступности на корректной тестовой цели. Отказ не означает доказанную причину «DPI».
- `INCONCLUSIVE`: DNS/целевой сервер/URL/VPN/очередь/сертификат/агент/таймаут с сомнительной причиной. **Не снимать лок и не уменьшать глобальный рейтинг как за достоверный FAIL**.
- HTTP статус 404/403/429 может быть ответом живого сервера, но **не всегда означает успешную работу сайта/видео**. TLS connection и app success — разные измерения.
- Если `nfqws2` не получил пакеты или фактически применил pass-through (`--autoexclude`, неверный план, ошибка Lua), результат независимо от HTTP 200 → `INCONCLUSIVE`.
- Перед критическими выводами проверять совпадение SNI/Host и IP назначения и отсутствие незаметного fallback HTTP/3→TCP.

### 2.4. Состояние задачи

`DISCOVERED → QUEUED → LEASED → PROBING → VERIFIED → CANDIDATE → APPLIED/REJECTED`, с исходами `CANCELLED`, `EXPIRED`, `INCONCLUSIVE`. Отдельное `strategy_catalog_version`. Каждый результат имеет уникальный `test_id`; повторный ответ не меняет состояние повторно.

## 3. Этапы реализации и приёмка

### Этап 0. Инвентаризация, замеры, контракты (без изменения продукта)

**Работы:**
- Зафиксировать состояние ветки `zator`, версий официального и fork `nfqws2`, профильных `strategy=N`, логику custom, `locked.lua`, Supersweep, webhook и данные Redis; определить реальные архитектуры/платформы.
- Замерить baseline CPU/RAM/пакетов nfqws2 на слабом OpenWrt/Keenetic, текущую память Redis (`INFO memory`, RSS), CPU/нагрузку, размер и число ключей, время построения `recommendations.py`.
- Записать версионированные протоколы агент↔Bash Zator и Zator↔сервер, набор причин ошибок, лимиты.
- Выбрать предельный тестовый budget и набор контрольных целей для основных сценариев.

**Приёмка:** можно восстановить исходное поведение/базовые метрики; архитектурный контракт не требует ZatorGO или дополнительных сервисов Redis на роутере.

### Этап 1. Доказать LAN→NFQUEUE изоляцию (важнейший go/no-go)

**Работы:**
- Существующий транспорт выделить в переиспользуемую часть и отдельный LAN-mode. **Нельзя просто скопировать правила OUTPUT/INPUT:** маршрутизируемый пакет приходит через PREROUTING/FORWARD и уходит после NAT; ответ возвращается в другой последовательности хуков.
- Тестовый агент запрашивает `lease`: протокол, IP клиента (определён роутером), выбранный исходный порт, destination IP:port, TTL, test_id. Проверить реальный 5-tuple. В фильтре — только действующий lease, никогда один `sport=62000-62999` для всего LAN.
- Согласовать/проверить bind исходного порта на Windows (стандартный dynamic range может пересекаться с `62000–62999`), Linux, macOS. Поддержать другой диапазон или конкретный выбранный порт; исключить захват обычного браузерного соединения.
- Оба направления попадания в **одну тестовую NFQUEUE** и обход основной; пометка conntrack для ответа; NAT, firewall marks, owner/UID injected packets, policy routing/VPN и flow offloading.
- Отдельный тестовый `nfqws2` использует **приватный** конфиг/локи и argv. Жизненным циклом владеет один процесс, mutex с фоновым Supersweep. Не убивать чужой процесс и не использовать занятую очередь.
- **Не путать номер запрошенной стратегии с реально применённой.** Сейчас `locked.lua` кеширует lock-файлы на ~2 секунды. При переключении кандидата нужен version/ack от тестового Lua или подтверждённая смена поколения таблицы; иначе быстрая последовательность запросов может измерять предыдущую стратегию. Не перезапускать `nfqws2` на каждый кандидат без доказанной необходимости.
- Для v1 изолировать только IPv4/TCP/443. При неподдерживаемом firewall/platform — отказ от активного теста без изменения основного трафика.
- Доказательство **фактического** прохождения тестового потока: состояние очереди и её счётчики + подтверждение обработки стратегия-выбора тестовым `nfqws2`; один общий счётчик недостаточен при конкурентных пробах.

**Приёмка:** на OpenWrt nft/fw4 и Keenetic iptables одно и то же тестовое соединение проходит test NFQUEUE; обычные подключения к этому же домену используют production NFQUEUE и не прерываются; при `nfqws2`-crash/firewall rebuild/отключении питания нет чужих временных правил и ложных `SUCCESS`. Правила Keenetic восстановимы после ndm rebuild. Отдельный отрицательный тест: HTTP 200 мимо очереди — недействительный результат.

### Этап 2. Минимальный агент ПК + локальный Bash API

**Работы:**
- Агент Windows MVP: фоновый процесс (позже tray), один тест за раз, `curl` с явным source port + `--resolve`, без proxy/redirect/Happy Eyeballs вне выбранного IP, ограничения времени/байт, TLS и HTTP/1.1; корректное завершение/таймаут.
- Локальный API через уже существующую Bash WebUI/CGI (не зависеть от ZatorGO): pairing только из LAN, короткоживущий токен, allowlist назначений/команд, проверка прав и размера запроса, обратная совместимость с отключённой WebUI (агент не запускается, ручной режим живёт). CLI команды для диагностики и отключения; не включать открытый listener на WAN.
- Агент **не принимает произвольные URL с сервера Redis**; тестирует только цели из локальной разрешённой категории или явно запрошенные пользователем.
- Один управляющий процесс на роутере: lease, процесс тестового `nfqws2`, состояние, конкуренция с Supersweep, отмена.
- При обрыве агента или смене DHCP/IP TTL lease истекает, тест признаётся `INCONCLUSIVE`, рабочие локи нетронуты.

**Приёмка:** тест на ПК по заданному hostname/IP идёт через отдельную NFQUEUE и возвращает JSON/TSV с подтверждённым тестом; ничего не меняется в production при закрытии агента, повторной отправке result, незавершённом HTTP запросе и параллельном агенте.

### Этап 3. Локальные динамические локи и согласованность стратегий

**Работы:**
- Реализовать в Bash хранение точных авто-правил, TTL, атомарные операции, лимиты RAM, уборку, отложенный snapshot на flash (не писать каждую пробу).
- Добавить в `orchestra/locked.lua` lookup после исключений/ручных правил, до групповых fallback; не менять старую `domain-grouping.lua` для существующего режима. **Точно разбирать dst IP и порт, видеть IPv4/IPv6, scope и протокол**, хранить решение на соединение.
- Стратегии каталогизировать как `(family/profile, semantic_hash, local_number, plan_version, compatibility_tags)`; hash вычислять при обновлении конфигурации, а не на каждом пакете. В hash включать нормализованные параметры, ссылки на значения blob/Lua и совместимую реализацию, без абсолютных путей и динамических параметров.
- Изменение blob/clone/mode/custom/версии nfqws2 инвалидирует несовместимые результаты или приводит к remap по точному `semantic_hash`; нельзя автоматически применять старый `strategy=N`.
- Разрешение конфликтов scope/домен/IP и смены правил в процессе соединения. Ручной lock/disable и исключения всегда выигрывают.

**Приёмка:** таблица exact host+IP сосуществует с другой для того же host на другом IP; обычные локи не меняются, переход между стратегиями без рестарта рабочего `nfqws2`; custom strategy с новым номером не наследует чужой рейтинг.

### Этап 4. Наблюдение + быстрый локальный подбор

**Работы:**
- Собрать **только события новых соединений** по релевантным hostlists: SNI/Host и DNS-наблюдение, IP, протокол, профиль, отметка времени. Привязка DNS hostname→IP с TTL и источником; не писать payload/полные URL, не ловить каждое соединение и не форкать процесс из Lua на пакет.
- Разделить `seen`, `suspected_failure`, `needs_verify`: посещение домена само по себе не доказывает блокировку. Очередь ограничить, дедуплицировать, проставлять cooldown/приоритет, поддержать кнопку ручного запроса.
- Если известный свежий лок — используем его без пробы; при неизвестном — немедленно применяем безопасный текущий fallback, запускаем **асинхронный** тест (первый пользовательский запрос не ждёт окончания перебора). 
- Порядок кандидатов: прежний локально подтверждённый → свежие рекомендации Redis → релевантные семейства → 1 исследовательский слот; удалять дубли по semantic hash; `DIRECT` включать отдельно.
- Проверить до **10** кандидатов в быстрой фазе, останавливаться после подтверждённого победителя. Если нет — углублённый поиск из остальных стратегий с ограничением нагрузки и явным статусом «не найдено».
- Двухступенчатые пробы: handshake+HTTP → реальная передача данных; выигрыш нельзя объявлять только по SYN/ServerHello/первому пакету. При сомнениях повторить, `INCONCLUSIVE` не менять лок.
- Адаптивное окно: первые проверки чаще, стабильный лок реже, сбои сокращают TTL; hysteresis: одиночный таймаут не выключает старое рабочее правило; контрольный `DIRECT` для различения проблемы сети.

**Приёмка:** один и тот же домен на двух IP получает независимые результаты; нет лавины проверок при открытии YouTube; на слабом роутере нет постоянного polling 0.3с/файловых обращений на каждый пакет; пользовательские соединения не прерываются во время перебора; при выключении агента старый режим продолжает работать.

### Этап 5. Серверная аналитика V2 поверх существующего Redis (1 vCPU, 2 ГБ)

**Работы:**
- Отдельные endpoints для `GET rankings`, `POST batch results`, опционально `GET exploration priorities`; старый `/z4r/recommendations.tsv` и загрузка полных SuperSweep остаются без изменений.
- Загрузки с клиента **батчами раз в 15–30 минут с jitter**. Ограничения: размер, число записей/батч, частота, список известных fingerprints, cap вклада установки в provider/profile/window, idempotency request_id. Сырые URL, полные истории посещений и IP пользователей не отправлять.
- Хранить компактные агрегаты провайдер × категория × протокол × semantic hash × ограниченное временное окно; **не хранить миллионы host×IP комбинаций**. Детализация по популярным CDN-кластерам только при пороге независимых наблюдений и строгом max cardinality.
- Пересчёт рейтинга cron/одиночным worker **раз в 5–15 минут** по изменённым группам; никакого HGETALL архивов в онлайн GET. Готовые rankings в Redis с TTL и/или генерируемый статический файл под nginx. `GET` без дорогого Python агрегирования.
- Рейтинг: сглаженная доля успехов, свежесть (например, 30 мин / 6 ч / 24 ч), независимость источников, совместимость со схемой стратегий, качество проверки и стоимость стратегии. Исторические полные Supersweep используют **только как слабый prior** из-за разных рецептов, IP и устаревших номеров.
- Сервер не присылает команды для выполнения, firewall-правила и произвольные тестовые URL — только валидируемые подсказки.
- Оставить Redis запас памяти под ОС/коллектор. Сначала измерить live-usage; ограничить **дополнительный расход V2** ориентиром 32–64 МБ с жёстким pruning. `maxmemory` менять только после оценки текущего сервера и overhead RDB/AOF/fork/CoW. Ограничить CPU budget фонового пересчёта и нагрузку HTTP.
- Автообновление рейтинга на роутере редко (10–30 минут, jitter); прежний кеш используется при сбое/429, fresh/stale отмечать.

**Приёмка:** 100/1000/10000 виртуальных клиентов в нагрузочном тесте, отсутствие регулярных пиков CPU/памяти, контролируемое поведение при Redis `OOM`, медленном диске, недоступном API, 429/503; старые endpoints работают; no remote autoapply. Реальная пропускная способность подтверждается тестом, не обещается заранее.

### Этап 6. Медленный полный исследовательский контур

**Работы:**
- В фоне проверять **и непопулярные стратегии**; очередь для актуальных доменов формировать локально и на основе агрегированных приоритетов. Отдельный низкоприоритетный бюджет, по умолчанию одна проба примерно раз в 2 минуты на ПК; отмена при срочном тесте, высокой загрузке/занятости канала, отсутствии агента.
- Локальный порядок гарантирует eventual coverage списка **только при достаточно долгой работе агента и повторных подходящих целях**; не обещать, что каждый пользователь проверит все N стратегий для каждого домена.
- Коллективное исследование по opt-in. Сервер публикует только приоритеты «недостаточно данных / давно не проверено / резкое ухудшение»; клиенты выбирают исследования через устойчивый hash псевдо-ID, окна времени и кандидата + случайность; **нет серверной per-client очереди**.
- Мягкие лимиты запросов к отдельной цели, jitter, cooldown, rate-limit после 429/потока RST, противодействие самообучающемуся рейтингу. Исследовательские результаты не должны автоматически заменять рабочий lock без отдельной подтверждающей пробы.
- Сбор статистики только с явно разрешённых и безопасных пробных целей; не инициировать массовое обращение к произвольным сайтам.

**Приёмка:** низкий приоритет соблюдается; отключение opt-in останавливает отправку и общественные задания; результаты новых стратегий всё равно начинают появляться в Redis; если сервер недоступен — локальная медленная проверка по согласию может продолжаться без зависания.

### Этап 7. Расширение: QUIC / Googlevideo / браузерные пробы

**Работы:**
- UDP-mode LAN-isolation отдельно тестировать до включения. QUIC не считать успешным по одному long-header; валидировать HTTP/3 **без fallback на TCP**, version negotiation/retry, реальную передачу.
- Для Googlevideo тестировать настоящие медиа URL (короткий свежий срок), независимый TCP и QUIC, upload/download path; контролировать истечение подписи, HTTP 403/404, валидность Range и размер теста. Не сохранять подписанные URL в Redis/логах.
- Для потоковых манипуляций `wssize_ramp`, `syndata` и иных зависящих от фазы TCP требовать долгую фазу передачи/скоростные метрики, ограничить общее число байт и WAN throughput; короткая HEAD-проба недостаточна.
- Браузерная верификация — дополнительный слой на ПК, не обязательный для MVP: curl и Chrome имеют разный ClientHello/TLS fingerprint. Результат снабжать `client_profile`, не распространять безоговорочно на иные клиенты.
- Поддержку IPv6, ECH, HTTP/2 connection coalescing, multi-WAN, policy routing, VPN-путей добавлять по тестовой матрице, при невозможности установить точную связь домен/соединение — fallback без точного авто-применения.

**Приёмка:** HTTP/3 fallback не засчитывается; работа TCP не скрывает неработающий UDP; реальные медиа загружаются устойчиво; throughput-тесты не перегружают слабый роутер.

### Этап 8. CLI/WebUI, эксплуатация, развёртывание и откат

**Работы:**
- CLI: `adaptive status|enable|disable|pause|test|logs|clear|doctor` (точные команды выбрать по текущему меню), отдельная настройка opt-in телеметрии и коллективного исследования.
- WebUI текущего **Bash Zator**: статус агента, очередь, домен/IP/протокол, применённая стратегия/источник, качество доказательства, TTL, ошибки тестовой очереди, объём нагрузки, кнопки «Проверить»/«Сбросить авто-правило».
- Не показывать сырые URL, IP клиентов и полную историю посещений в общедоступных логах и телеметрии. Учитывать auth CGI, CSRF и localhost/LAN binding.
- Режимы: OFF (ничего не меняет), OBSERVE (только наблюдение), TEST_ONLY (можно тестировать, не применять), AUTO (применение после валидации). По умолчанию OFF или TEST_ONLY в пилоте.
- Добавить новые файлы в `z2r.sh`, `z4r` launcher, обновления/backup/restore/uninstall, учитывать `/opt/zapret2` как временный upstream root и `/opt/zator` как постоянный root; сделать безопасную миграцию и rollback.
- CI/smoke: Bash/ash-недостатки, `set -e`, блокировки, `SIGINT/SIGTERM/SIGKILL`, нет `setsid`, nft/native hooks, iptables 1.4.21 (bare `-w`), перезапись ndm. 
- Внедрение: сначала тесты OpenWrt nft + Keenetic iptables, затем opt-in небольшая группа, затем массовая доступность; режим авто — после доказанной надёжности.

**Приёмка:** OFF полностью восстанавливает старую модель и снимает свои firewall правила; сохранённые ручные локи не потеряны при обновлении/откате; после reboot/power loss состояние восстанавливается без hanging lock.

## 4. Список критических edge cases (проверить явно)

### Сеть/изолятор
- Windows dynamic ports пересекают `62000–62999`; у agent source bind ошибка, порт успел занять браузер, исходный порт поменялся на повторном HTTP запросе.
- NAT/CGNAT, маршрут через VPN/PBR, lan bridge, IPv6, DNS64/NAT64, dual-stack/Happy Eyeballs. Проба и реальный трафик **должны идти через одинаковый WAN/маршрут** — иначе результаты нерелевантны.
- Одна машина имеет два IP/NIC, DHCP сменился, второй агент в той же LAN, Wi-Fi/VLAN/guest network. Lease привязан к фактически увиденному LAN IP и destination tuple.
- Firewall rebuild Keenetic, OpenWrt fw4 reload, offload/fastpath может обходить NFQUEUE, порядок nft-hook, `accept` в соседней base chain не останавливает другие base chains. Отсутствующая очередь с `--queue-bypass` не должна давать SUCCESS.
- `nfqws2` inject/raw packets не должны попадать в рабочую NFQUEUE или зацикливаться на тестовой; route-mark и uid 65533 проверять с текущим Supersweep.
- Несколько test/supersweep одновременно — один владелец NFQUEUE/транспортного модуля; timeout и cleanup только своих ресурсов.
- Роутер перезагрузился после lease, агент получил timeout, повторил, сервер дважды получил результат. Идемпотентность.

### Протокол и валидатор
- HTTP 403/404/429, captive portal, DPI заглушка, TLS certificate mismatch, TLS1.2 vs 1.3, ALPN h2/h1, proxy, редирект на другой домен, статус без тела, сжатие/Range ignored, QUIC↔TCP fallback.
- Несуществующая или временно сломанная цель, DNS-poisoning и split DNS, смена CDN IP между тестом и реальным клиентом, expired Googlevideo URL, 206 с слишком маленьким содержимым, искусственный серверный rate limit.
- `DIRECT` успешен, а desync ломает; в этом случае не пытаться насильно назначить top-1. Смена правил DPI во время 10 проб → не сравнивать результаты как одну стабильную эпоху.
- Клиентский TLS fingerprint curl отличается от браузера; стратегия pass для curl не доказывает pass для Chrome.
- Много протоколов/поддоменов за одним TCP/H2 соединением, ECH/DoH скрывает hostname, IP одного CDN обслуживает посторонние домены; **никаких широких IP lock без доказательства scope**.

### Производительность/надёжность
- Тысячи посещённых поддоменов, один сайт генерирует пачку новых DNS/SNI, инкрементальные обновления Lua cache и файл в /tmp; ограничивать записи и RAM, LRU/TTL.
- Глобальные host records внутри `nfqws2` и conntrack/NAT-таблицы тоже расходуют память: помимо локального TSV ограничивать число активных тестовых соединений, таймауты и кеши Lua.
- Быстрый поиск из 10 стратегий может занять минуты при паузе для rate limits; не блокировать браузер и не запускать новый поиск по каждому повторному соединению. Переход между кандидатами требует подтверждения смены **именно применённой** стратегии в тестовом `nfqws2`, не только нового значения в `locked.tsv`.
- Короткие проверки создают ложные успехи для `wssize_ramp`, а длинные могут заполнить WAN и загрузить CPU роутера; ограничивать CPU/пакеты/байты.
- Переполнение `/tmp`, флеш изношен частыми fsync/write, `Bash set -e` убивает service, `mv` неатомарен между разными FS, orphan `write-lock`, respawn loop после фатальной ошибки.
- Redis AOF/RDB fork+copy-on-write, disk full, Redis out-of-memory, 1-vCPU пики Python обработки, cache stampede, клиентский thundering herd после обновления; TTL+jitter+ограничения batch/cardinality.
- Телеметрия фальсифицируется, UUID может меняться, одна установка шлёт тысячу успехов, клиент помечает `INCONCLUSIVE` как `FAIL`. Стабильный fingerprint не равно стратегическому номеру.
- Опт-ин/отзыв согласия: статистику посещений не загружать; только разрешённые агрегаты. Нет входящих команд от сервера; лимиты для предотвращения использования клиентов в генерации вредного трафика.

## 5. Начальные бюджеты и защитные ограничения (настройки, не доказанные оптимумы)

| Лимит | Стартовое значение | Что делать при превышении |
|---|---:|---|
| Активные тесты на роутер | 1 | Очередь/отмена фонового |
| Кандидатов в fast-фазе | 10 + отдельный DIRECT | При провале → расширенный поиск |
| Фоновая проверка ПК | Не чаще 1/120 c | Пропуск при busy, лимит WAN |
| Батч телеметрии | Каждые 15–30 мин с jitter | Локальный ограниченный spool, drop oldest или backoff |
| Кеш рейтинга | 10–30 мин с jitter | Stale fallback |
| Пересчёт server-rank | 5–15 мин | Пропуск при высокой нагрузке |
| TTL первоначально подтверждённого авто-лока | 15 мин | Продлевать после успешной перепроверки |
| Обновления правил Lua | По изменению, с cache | Не перечитывать файлы на каждый пакет |
| Budget Redis V2 сверх baseline | Первоначальная цель 32–64 МБ | Урезать детализацию/горячие группы, TTL/pruning |
| Источники v1 | Windows агент + OpenWrt/Keenetic IPv4/TCP | Остальные платформы работают в fallback |

Частоты и размеры надо измерить. Базовые 15/30 секунд паузы Supersweep были введены против поведенческих ограничений DPI: в быстром поиске нельзя бездумно сделать 10 запросов подряд к одному CDN; отдельно измерить скорость/вероятность rate limiting и настроить per-target pacing.

## 6. Обязательные тесты, результаты и критерии включения AUTO

Сценарии для регрессий:
1. Manual locks/profile/scope, исключения, выбор host/IP и динамический fallback (Lua tests).
2. Каждая комбинация `SUCCESS/FAIL/INCONCLUSIVE`, wrong queue, wrong route, expired URL, TCP без HTTP3, duplicate/test_id race.
3. OpenWrt fw4/nft, Keenetic iptables (+ndm reload), официальная и fork сборки nfqws2.
4. Windows source binding + LAN NAT+connmark+return path, обычный браузер на том же домене не задет.
5. 2 одновременно подключённых агента, потеря питания/HTTP сессии, cleanup и stale PID.
6. Изменение конфигурации, custom-strategy remap, clone blob, обновление zapret2, backup/restore.
7. Длительный тест слабого роутера с лимитами CPU/RAM/WAN и учётом offload.
8. Нагрузочный тест Redis/HTTP имитацией 100, 1000 и 10 000 клиентов; p95 задержки, RSS, fork AOF/RDB, disk budget и rate-limits; **не декларировать масштаб до измерения**.

**Go/no-go для AUTO:**
- Все тестовые соединения подтверждённо проходят test NFQUEUE; ни одного ложного SUCCESS из пропущенной очереди.
- Быстрые/фоновые тесты не меняют рабочие локи до окончательной валидации.
- Любой сбой агента, firewall, Redis, RPC, Lua, reboot безопасно переводит систему в прежний рабочий режим.
- На целевых слабых роутерах измерены и соблюдаются ресурсные бюджеты.
- Конфигурации и версии стратегий не смешиваются в статистике.
- Испытания сети и тестов не обнаружили массового ложного переключения при изменении CDN/DNS/HTTP-статуса.
- Режим OFF и удаление агента не требуют ручной чистки очередей и firewall.

## 7. Рекомендуемый порядок PR / работ для агента-разработчика

1. **PR-A: Contract + inventories + tests** — зафиксировать JSON/TSV v1, semantics ID/вердиктов, baseline.
2. **PR-B: `LAN isolated probe`** — транспорт и PoC без Redis, без auto-apply; критический gate.
3. **PR-C: PC agent MVP + authenticated Bash CGI** — только один конкретный тест из меню/команды.
4. **PR-D: local rule store + Lua lookup + tests** — exact host/IP, ручные локи, TTL, интеграция без рестарта.
5. **PR-E: discovery + scheduler + fast ranking (пока локальный/статический)** — 10 кандидатов, direct, два уровня валидации.
6. **PR-F: server v2 aggregates + ratings + caching** — только после измерения существующего VPS.
7. **PR-G: slow local exploration + opt-in collaborative** — без отдельного серверного планировщика.
8. **PR-H: QUIC + Googlevideo real media + IPv6 (возможно отдельными PR)**.
9. **PR-I: Bash WebUI/CLI UX + rollout/rollback/operational checks** — UI можно добавлять итеративно, но финальная приёмка обязательна.

**Точка проверки после PR-B:** если изоляция LAN-трафика на Keenetic/OpenWrt неустойчива или требует постоянного выключения hardware offload, **не продолжать автоматическое применение**. Рассмотреть тестирование через отдельный endpoint/виртуальный IP/прокси или ограничение функции поддерживаемыми платформами.

## 8. Основные открытые инженерные гипотезы (доказать тестами, не угадывать)

1. Достаточно ли `nfqws2`/firewall маркировки для надёжного совпадения тестового и пользовательского WAN-маршрута при реальном PBR/VPN?
2. Можно ли из Lua дешёво извлечь и правильно связать destination IP с host, особенно при фрагментации и QUIC?
3. Какую именно проверку считать успехом Googlevideo — handshake, Range 64 КиБ, 1–2 МБ, стабильный throughput? Подобрать безопасные уровни.
4. Как быстро можно тестировать 10 стратегий подряд без rate-limit провайдера, не заставляя пользователя ждать?
5. Достаточно ли актуальной телеметрии provider/profile для ранжирования по конкретным CDN-кластерам, или сначала нужен локальный history-only режим?
6. Реальный лимит Redis/HTTP на 1 vCPU / 2 ГБ RAM при сохранении старых сервисов и периодических RDB/AOF.

**Окончательный принцип:** новая система должна улучшать шанс быстрого восстановления доступа, а не превращаться в обязательный сетевой посредник. При любой неопределённости сохранять обычный трафик и знакомые механизмы Zator.
