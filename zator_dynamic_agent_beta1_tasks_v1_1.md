# Zator Bash — доработки до Beta 1 «Динамический агентский подбор»

**Тип документа:** техническое задание и план реализации для coding-агента.  
**Дата:** 2026-11-21.  
**Репозиторий:** `AloofLibra/zator`.  
**Исходная ветка для доработок:** `feat/bash-adaptive-rotation` (перед работой сверить с актуальным `zator` и проверить новые коммиты).  
**Целевая система:** действующий **Bash Zator**, **не ZatorGO**.  
**Релизная цель:** **Beta 1: «Динамический агентский подбор»**, а не обещание полноценной автономной авторотации.  
**Редакция:** v1.1 — уточнена стратегия Googlevideo: **Ramp-first для всего известного пула с фоновым поиском точных исключений и CDN-группировкой**.

> **Главное требование:** к Beta 1 обязаны работать **TCP/TLS**, **Googlevideo TCP с реальным `wssize_ramp` и автоматическим фоновым отключением Ramp там, где он не нужен**, **Googlevideo QUIC/HTTP3**, локальное применение проверенных решений и безопасный откат. Никаких «готово» по одному HTTP 200 или по прохождению smoke-тестов. Для двух аппаратных семейств нужны подтверждённые интеграционные тесты.

### Зафиксированная отправная точка

- Есть TCP/443 IPv4 TEST_ONLY: Windows PowerShell 5.1 агент, CGI, lease по tuple, test queue `65535`, отдельный `nfqws2`, Lua ACK, локальный `rules.tsv`, discovery/Watch, FastSearch и Explore.
- На **отдельных конкретных** OpenWrt и Keenetic прошли парные LAN/production-потоки. Это не подтверждение всех маршрутов, offload, сборок `nfqws2` и длительной стабильности.
- `AUTO` пока недоступен; WebUI и CLI имеют прототипные элементы управления.
- Redis V2 существует и испытан на отдельной тестовой VM; **production stats-host не менялся**. Старые статистические endpoints должны остаться рабочими.
- **Критическое ограничение:** в `lib/supersweep_probe.sh` явно выполняется `ramp_enable=0`, поэтому отдельная TCP-проба **не измеряет Ramp**.
- `lib/quic_media.sh` уже умеет проверять настоящее Googlevideo HTTP/3, но её текущий маршрут — через **production `nfqws2`/production lock**, не через агентскую изоляцию.
- FastSearch может остановиться на `DIRECT / INCONCLUSIVE timeout`, даже не проверив стратегии. DeepSearch доступен вручную, но не является автоматическим продолжением.
- Используется точный host+IP+scope, но режим `AUTO` пока не подключён к наблюдению/Watch; успешный DIRECT не становится применимым локальным правилом.
- Семантический fingerprint недостаточно отделяет TLS-стратегию от фактических режимов clone/blob/SNI/Ramp и других влияющих параметров.

**Не считать документацию доказательством отсутствия проблем.** Вначале выполнить ревизию кода и добавить воспроизводящие тесты для перечисленных сценариев. Если исходная ветка уже изменилась — адаптировать задачи, не повторяя исправления.

## 2. Что должен получить пользователь

1. Пользователь явно включает на роутере «Динамический агентский подбор (Beta)» и запускает сопряжённый Windows-агент.
2. Агент наблюдает доступные маршрутизатору события и **асинхронно** проверяет перспективные варианты. Первый пользовательский запрос никогда не удерживается в ожидании тестов.
3. Для обычного TLS: перебор до 10 кандидатов с локальной проверкой; при отсутствии успеха **автоматически** продолжается ограниченный DeepSearch в низком приоритете (с паузами и восстановлением после рестарта агента).
4. Для Googlevideo TCP: после локального подтверждения необходимости Ramp включается **управляемая политика Ramp-first для всего известного Googlevideo IP-пула**; агент **в фоне** сравнивает Ramp и обычный TCP **только на реально посещённых пользователем host/IP**, формирует подтверждённые IP-исключения без Ramp и продолжает использовать обычный TLS-подбор на этих адресах. `syndata` — отдельный необязательный вариант только совместно с Ramp.
5. Для Googlevideo QUIC: подбор стратегий профиля `5` по **реальному HTTP/3**, без скрытого перехода на TCP; оценка передачи медиа, а не только UDP-пакетов.
6. Подтверждённый выбор применяется только в своём контексте и **не переписывает ручные локи**. Возможен безопасный `DIRECT` (без desync) и откат.
7. Redis нужен для подсказки очередности и статистики, **никогда не назначает стратегию без локальной проверки**. Нет сервера/нет согласия на общую статистику — локальный подбор продолжает работать.
8. Интерфейс честно показывает статус агента, причину успеха/неопределённости, использованный тестовый рецепт и уровень подтверждения.
9. Для Googlevideo хосты группируются **по устойчивой CDN-части имени**, а не целиком в `googlevideo.com`: результаты соседних `rrN`-хостов ускоряют **выбор кандидатов**, но не заменяют подтверждение отключения Ramp для конкретного IP.

### Продуктовые ограничения Beta 1

- Поддержка: **IPv4; TCP/TLS для профилей 1–4; UDP/443 для Googlevideo/YouTube профиля 5**. Не обещать голосовой Discord, произвольные игры, IPv6 или универсальную UDP-авторотацию.
- В первой бете **Windows PowerShell 5.1** агент обязателен для расширенных проверок. Автономную полноценную авторотацию на роутере отложить.
- Для сложных механизмов **не строить полный комбинаторный перебор параметров**. Поддержать ограниченные осмысленные варианты, описанные ниже.
- Если beta-требования не прошли hardware gates на платформе, функциональность там должна быть выключена/помечена неподдерживаемой; нельзя молча переходить к production-переключению локов.

## 3. Неприкосновенные инварианты

- **Ручные локи, ручные отключения, `netrogat`, профильные hostlist/gate, client scopes, текущие профили и старый Supersweep имеют приоритет.** Авто-правила — отдельный слой, не вписывать их в `locked.tsv`/`locked.manual.tsv`.
- Тестовый поток только по подтверждённому точному lease и **только через собственную NFQUEUE**; рабочий трафик через штатную очередь. Не менять production-стратегию ради теста.
- Сбой probe, агента, Lua, firewall, CGI, Redis или машины → не применить новое правило; при `disable`/`pause` собственные временные правила/процессы удаляются, чужие не затрагиваются.
- `SUCCESS` только при проверенных маршруте, подходящем обработчике, выбранной стратегии и прикладном результате. `INCONCLUSIVE` не превращать в `FAIL` и не использовать для ухудшения серверного рейтинга.
- Запрещены произвольные URL, команды и firewall-политики со статистического сервера. Подписанные медиассылки и личные IP/домены не загружать в Redis.
- Все данные/процессы ограничены по CPU, RAM, времени, размеру, числу записей, частоте и количеству тестового трафика. На слабом роутере — один активный probe.
- Изменение стратегии **не должно** менять уже установленный TCP/QUIC flow посреди передачи. Применять новое решение к новым соединениям.
- Сохранить совместимость обеих корневых директорий: `/opt/zator` (постоянное состояние) и `/opt/zapret2` (upstream), а также обновлений, backup, rollback и offline package.

## 4. Порядок реализации: небольшие PR, не один гигантский рефакторинг

### PR-B0. Исправление TCP FastSearch и цепочки состояний — **P0**

**Что изменить**

1. Исправить остановку на `DIRECT / INCONCLUSIVE timeout` и на обычном таймауте кандидата. **Одиночная неудачная попытка не доказывает, что стратегия плохая**, но при исправном тестовом окружении не должна прекращать поиск остальных вариантов.
2. Разделить причины на:
   - **фатальные для тестового окружения**: нет владельца test NFQUEUE, неверный route/lease/tuple, чужая очередь, неверный ACK, отмена, неконсистентный каталог, критическая ошибка агента/контроллера;
   - **неокончательный результат кандидата**: timeout, отсутствие ответа, отдельный TLS/RST/HTTP reject без подтверждения, ограниченный размер ответа;
   - **ограничения цели**: 429, 5xx/временная недоступность, rate limit — временно остановить/отложить тестирование именно цели, не применять `FAIL`;
   - **подтверждённый SUCCESS**: корректный transport и необходимый application recipe.
3. Для таймаутов **до ClientHello** предусмотреть диагностические признаки `queue_seen`, `strategy_ack_seen` и `phase_reached`: при отсутствии ACK нельзя объявлять SUCCESS/FAIL, но валидный факт прохождения SYN через тестовую очередь позволяет завершить *кандидата* как INCONCLUSIVE и продолжить безопасный ограниченный поиск, если неисправность транспорта не доказана. Не ослаблять обязательность ACK для SUCCESS.
4. Вынести механизм переходов в тестируемые функции: `candidate unknown → next candidate`, `route broken → stop`, `429 → cooldown`, `success → stop`. Проверить поведение по TCP/TLS 1.2 и 1.3, не смешивая протокольную и прикладную доступность.
5. Десять кандидатов — **предел быстрой фазы**, не предел всего подбора. Если 10 исчерпаны без успеха, **автоматически поставить продолжение** с остальными семантически уникальными стратегиями. Выполнять порциями, только при свободном бюджете, без длинного блокирования Watch. Предусмотреть честные статусы `fast_exhausted`, `deep_scheduled`, `deep_running`, `all_exhausted`, `stopped_infra`, `stopped_rate_limit`.
6. Не повторять одни и те же 10 стратегий при новых посещениях того же домена. Персистентный (ограниченный) cooldown/курсор для exact host+IP+profile+scope+recipe+catalog; сбрасывать при смене каталога и учитывать новые IP/истечение TTL.
7. Приоритет: ручной `needs_verify` → подозрение поломки активного правила → быстрый поиск → DeepSearch → фоновый Explore. Один слот probe, корректная отмена только своей работы.
8. Замерять длительность каждого шага и время до первого SUCCESS. Не пытаться скрывать задержку за коротким, но недостоверным тестом.

**Приёмка:** `DIRECT` timeout и последующая рабочая стратегия №N приводят к её проверке; 10 неудачных кандидатов дают поставленный DeepSearch; отсутствие test queue никогда не даёт SUCCESS; 429 не превращается в негативный Redis-результат; обычный браузер не блокируется ожиданием.

### PR-B1. Безопасный beta-режим, применение, DIRECT, повторная проверка — **P0**

1. Добавить **явный отдельный opt-in** для фактического применения. Пользовательское название — «Динамический агентский подбор (Beta)». Рекомендуемый внутренний режим — `AGENT_BETA` либо совместимый feature gate над существующим `AUTO`; **не включать старый `AUTO` обходным путём** и не нарушать переходы OFF/OBSERVE/TEST_ONLY.
2. Исправить жизненный цикл: в применяющем режиме продолжаются discovery/Watch, lease, тесты, очереди и обновление правил. Сейчас `locked.lua` включает наблюдение только в OBSERVE/TEST_ONLY, а CGI/controller ограничены TEST_ONLY — привести всю цепочку к согласованной модели.
3. Сохранять `DIRECT` как **отдельный валидированный вариант без desync**, с TTL, exact scope и условиями применения. Не записывать его как неподтверждённый произвольный номер `strategy=N`; для Ramp/SYN нужно доказать, что DIRECT действительно означает отключение и ранних, и поздних воздействий тестового профиля.
4. Проверять **реальный client scope** в Lua ACK и маршруте (не только scope, переданный в lease). При невозможности подтвердить действительный scope — `INCONCLUSIVE`, не применять scoped-правило.
5. Точные auto-правила: host+destination IPv4+protocol+profile+scope+**treatment variant**+runtime/catalog stamp+TTL. При конфликте/неоднозначности не применять. Ручной домен и ручной профиль должны выигрывать согласно старой семантике. **Не распространять результат Windows curl на все устройства локальной сети без явного разрешения:** в Beta по умолчанию применять только для подтверждённого клиентского scope, а если доступен лишь `default` (общий для LAN), требовать отдельный opt-in на действие для всей сети или оставить TEST_ONLY. Продумать привязку к наблюдаемому устройству, не делать вид, что `default` означает «только этот ПК».
6. Расширить сигнал `suspected_failure` на **уже применённое авто-правило**, а не только на неразрешённые host/IP. Повторная активная проверка по сигналам ухудшения, но **одиночный timeout не снимает правило**. Ввести hysteresis и cooldown против постоянного переключения.
7. Разделить время жизни **проверки**, **применённого решения** и **кулдауна перепроверки**. Не удалять рабочее правило только потому, что Redis недоступен. После истечения доверия — переаттестация либо возврат к известному локальному fallback по безопасной политике.
8. Переключения в production допустимы **только на новых соединениях**; без рестарта рабочего `nfqws2` для каждого кандидата. Для приложений с долгоживущими TCP/QUIC-соединениями старый flow не трогать.
9. `disable`/`pause`/uninstall/restart/backup восстановление: атомарность, fail-safe cleanup, revocation, отсутствие висячих fw-rules или чужих процессов. Проверить recovery после SIGKILL, reboot/power loss и firewall reload.

**Приёмка:** подтверждённый DIRECT убирает вредный desync для следующего соединения; корректный лок применяется автоматически только после opt-in; сломанная ранее применённая стратегия инициирует перепроверку; ручной лок нельзя перебить; OFF возвращает старое поведение.

### PR-B2. Googlevideo TCP media recipes — **P0**

1. Добавить явную категорию `googlevideo_tcp`, отличную от обычного TLS-контроля. Использовать проверенные функции получения видео/аудио ссылок из `lib/youtube_media.sh`; при необходимости выделить небольшой чистый слой для совместного использования `supersweep` и `adaptive`.
2. **Не использовать `https://googlevideo.com/` и любое случайное `/` как доказательство работоспособности видеопотока.** Нужно делать HTTP Range по настоящему медиа-ресурсу с пригодным, неистёкшим signed URL.
3. Обработка refresh подписанных URL, 403/404/429/5xx, отсутствия Range, малого контента, ограничений источника; различать `origin_unavailable`, `signed_url_expired`, `rate_limited`, `transport_timeout`, `media_insufficient`, `media_ok`. Неправильный URL не снижает оценку стратегии.
4. Для быстрых проб использовать короткий L1/L2; для принятия решения о Googlevideo — обязательный **L3 media** с объёмом и продолжительностью, достаточными для проверки поздних ACK и поведения Ramp. Стартовый контрольный объём, например 1–2 МиБ, плюс проба другого фрагмента/повтор для сомнительных случаев. Конкретные минимумы/скорости выбрать по измерениям, не по догадке. Установить верхние лимиты байт и времени.
5. Сравнение скорости делать между кандидатами на **сопоставимом URL/CDN/IP/recipe и в разумном временном окне**. Если CDN/IP или signed URL сменились, начинать новый набор измерений; нельзя трактовать эту разницу как выигрыш стратегии.
6. Соблюдать `--resolve`/pinned destination IP, отсутствие proxy, редиректов, скрытого TLS/QUIC fallback. Если невозможно подтвердить, что агент и реальный клиент вышли тем же WAN/маршрутом, понижать уверенность/не применять широкое правило.
7. В `rules.tsv` и статистике не смешивать `tls-http1-v1` с `googlevideo-tcp-media-v1`; сохранять уровень подтверждения: handshake != HTTP != media.
8. Никакие signed URLs, cookies, media bodies, IP пользователя и история посещений не отправляются в Redis; временные URL держать в приватном tmpfs, логировать только безопасные коды и метрики.

**Приёмка:** стратегия с успешным TLS, но провалом реальной передачи данных **не** получает статус `googlevideo_media_success`; ошибочный/истёкший URL не считается `FAIL` стратегии; работающий real media получает измеренный throughput и подтверждённый маршрут test NFQUEUE.

### PR-B3. Googlevideo TCP: Ramp-first, фоновое исключение ненужного Ramp, CDN-группировка — **P0, обязательный beta gate**

**Уточнённая продуктовая модель (важнее первоначальной схемы):**

1. Стартовая точка — обнаружен и подтверждён Googlevideo host/IP, для которого обычный TCP не обеспечивает корректную передачу медиа, а TCP+`wssize_ramp` обеспечивает. По явному beta-opt-in пользователя включить **Ramp для всего известного Googlevideo IP-пула** (локальный и центральный валидированный список; не для всего TCP/443). Это осознанное расширение зоны применения и потому требует прозрачного статуса и мгновенного отката.
2. После включения не делать полный Supersweep по всем Googlevideo адресам. **Пассивно наблюдать, к каким host/IP действительно обращаются устройства пользователя.** Только для таких назначений запускать **незаметные пользователю фоновые активные изолированные пробы** `Ramp ON` / `Ramp OFF`, с ограничениями трафика/CPU и без изменения работающих соединений. Здесь «пассивно» относится к обнаружению целей и низкоприоритетному планированию; сами проверки — активные, иначе сравнить варианты достоверно невозможно.
3. Если на конкретном адресе подтверждено, что без Ramp реальный медиапоток работает с приемлемыми стабильностью и скоростью, создать **точное временное исключение из Ramp**. Этот IP продолжит проходить **обычный TCP/TLS трек Zator** и подбор TLS-стратегий. Это **не** означает `DIRECT` и не отключает стандартную обработку DPI.
4. Для остальных адресов, не проверенных или имеющих неопределённые результаты, **Ramp остаётся включённым**. Если адрес начал деградировать без Ramp, исключение отзывается и возвращается Ramp.
5. **Группировать близкие Googlevideo hostname по CDN-суффиксу**, чтобы не проверять практически одинаковые `rrN`-варианты с нуля. Однако групповой успех — основание поднять проверенные стратегии в очереди, **не основание автоматически выключить Ramp для ещё не проверенного IP**.

**Архитектурное ограничение:** `wssize_ramp` и `syndata` воздействуют уже при SYN/Window Scale и на поздних ACK; на SYN SNI обычно неизвестен. Поэтому применяемость Ramp/исключений в production определяется **destination IPv4 до SYN**, используя управляемые IP-наборы и доступную DNS↔IP атрибуцию. Доменные правила ниже дают рекомендации, но не обещают невозможного per-domain SYN-переключения для нескольких hostname на одном IP.

**Минимальный каталог вариантов для Googlevideo:**

| ID варианта | SYN / начало потока | TLS | DATA / ACK |
|---|---|---|---|
| `gv_tcp_plain` | Обычный TCP, нет Ramp и `syndata` | Выбранная TLS-стратегия | Обычная обработка |
| `gv_tcp_ramp` | Ramp с текущими параметрами пользователя | Та же TLS-стратегия | `wssize_ramp` full/lite |
| `gv_tcp_ramp_syndata` | Ramp + явно включённый `syndata` | Та же TLS-стратегия | `wssize_ramp` |

#### B3.1. Изолированное сравнение и модель включения Ramp

1. Убрать безусловное `ramp_enable=0` **только для нового adaptive Ramp recipe**. Старые isolated Supersweep и исторические матрицы не менять. Генератор тестового `nfqws2` должен получать явный `recipe/treatment_variant`.
2. В отдельную test NFQUEUE направлять **SYN, ClientHello, поздние DATA/ACK** в обе стороны; подтверждать фактически применённый ранний режим и отсутствие offload bypass. При отсутствии подтверждённого SYN/поздних пакетов — `INCONCLUSIVE`.
3. Для `plain` и `ramp` брать **один фактически посещённый hostname, один destination IP, одну TLS-стратегию и сопоставимый настоящий signed media URL**; проверять pinned IP и одинаковый WAN/маршрут. Если доступный media URL имеет другой hostname и нельзя корректно протестировать исходный host/IP, **не заявлять проверку этого адреса**.
4. Для сравнения применить короткую L1/L2-проверку, затем ограниченную L3 media. Сравнивать не только HTTP-статус, но достаточный объём, скорость, остановки/обрывы, поздние ACK и устойчивость. Два независимых подтверждения `plain` (на новых соединениях в разные моменты) — рекомендуемый стартовый минимум; точные пороги, интервалы и допустимый проигрыш скорости по отношению к Ramp определить экспериментально. `plain` не должен быть существенно хуже Ramp и обязан проходить минимальную полезную скорость.
5. Чередовать порядок `Ramp → Plain` и `Plain → Ramp` между измерениями, при неоднозначности повторять/использовать контроль `A→B→A`. Иначе можно принять изменение состояния DPI/CDN за свойство Ramp. 403/429, истёкшая подпись, другой IP или исчезновение медиаданных дают `INCONCLUSIVE`, **не** «Ramp нужен» и **не** «Ramp не нужен».
6. Чтобы включить Ramp-first на **весь известный Googlevideo IP-пул**, сначала локально подтвердить исходный Ramp-required кейс (`Ramp` проходит медиарецепт, `plain` не проходит или явно ниже полезного порога при сопоставимом контроле) **или** принять явное ручное указание пользователя, пометив основание как `manual_unverified`. Автоматическое расширение должно быть отдельным opt-in для затронутого LAN/scope; не менять ручной глобальный параметр Ramp молча.
7. Предполагаемые beta-параметры Ramp (`mode`, `wsize`, `scale`, `open`, `syndata`, blob) брать из действующей конфигурации и включать в effective fingerprint. Не перебирать их декартово произведение. `syndata` **всегда** отключается вместе с Ramp для `plain`-исключений.
8. Тестирование должно быть независимым от текущих production Ramp-правил: `plain` в тестовой NFQUEUE **доказанно обходит production Ramp**, а `ramp` — использует только изолированный Ramp. Если разграничение невозможно, результаты недействительны.

#### B3.2. Наблюдения и планирование фоновых проб

1. Источник целей — **только фактически посещённые пользователем Googlevideo host/IP** из существующего наблюдения трафика Zator и/или локального Googlevideo DNS collector. Серверный IP-feed служит **пулом применения Ramp**, а не списком задач на массовый перебор. Не сканировать все адреса пула, не порождать пробы для непосещённых доменов.
2. Писать локальные bounded события `host`, `ip`, `scope`, `last_seen`, `provenance`, `dns_expires_at` (если известно), `group_id`, состояние Ramp, доступность валидного media recipe. Дедуплицировать по `host+ip+scope`, ограничить память и размер tmpfs. Если SNI/DNS нет — можно учитывать наблюдённый IP, но **не выдумывать** имя и не применять групповые выводы.
3. Фоновая очередь Ramp-аудита должна быть **ниже** ручной проверки, восстановления сломанного правила и FastSearch, конкурировать за **один общий probe slot**, иметь устойчивый cursor/cooldown и не повторять уже недавно проверенное. Начальный ориентир — не чаще одного **набора сравнительных проб** на реально посещённую цель за несколько минут и лишь при низкой загрузке; числа уточнить после hardware-замеров. Не считать пару A/B за одну бесплатную пробу в расчёте бюджета трафика.
4. При повторном обнаружении `rrN`-соседа из проверенной группы: сначала использовать успешные групповые TLS-кандидаты и известное предварительное заключение о Ramp **для приоритизации короткого exact host/IP теста**; не делать полный перебор. Сохранять разнообразие исследуемых семейств; не застревать навсегда на единственном победителе.
5. Если стабильный `plain` доказан, обновить локальный state и ipset/nft set для новых соединений без перезапуска рабочего `nfqws2` и без записи на flash по каждой пробе; при истечении TTL или деградации восстановить Ramp. В UI показывать: `Ramp default / Ramp exempt / Pending / Conflict / Uncertain` и причину.

#### B3.3. CDN-группировка без ложных объединений

1. Сделать **отдельную нормализацию ключей адаптивного подбора**; не использовать нынешнюю грубую группировку всех поддоменов в `googlevideo.com` как единственный ключ для решения. Старую `lua/domain-grouping.lua`/ручной режим не ломать.
2. Группировать **только известный и строго разобранный CDN-шаблон**, меняя **исключительно индекс `rrN`** при неизменном остальном hostname. Примеры:
   - `rr1-index.googlevideo.com` и `rr2-index.googlevideo.com` → одна группа `gv:rr:index`;
   - `rr1-index2.googlevideo.com` → **другая группа** `gv:rr:index2`;
   - типичные `r1---sn-XXXX.googlevideo.com` и `r2---sn-XXXX.googlevideo.com` → одна группа **только если весь суффикс `---sn-XXXX.googlevideo.com` совпал**; `rN` и `rrN` сохранять разными семействами.
   - `redirector.googlevideo.com`, неподходящие hostname и неоднозначные шаблоны → **точный ключ**, не обобщать.
3. Нормализовать lowercase и конечную точку; проверять границы DNS-меток и реальную принадлежность `googlevideo.com`, не сопоставлять `evilgooglevideo.com`. Не удалять цифры из `index2`, `sn-...`, произвольной части имени и не объединять различные CDN-сегменты по одному eTLD+1.
4. Хранить **два уровня идентичности**: `group_id` для ускорения **ранжирования TLS-кандидатов и выбора следующих фоновых проб**, `exact host+ip+scope` для доказательств и конкретных Ramp-исключений. Для нового IP из уже проверенной группы делать ускоренную локальную проверку, но **не наследовать автоматически IP-исключение**.
5. Групповые данные включают число **различных hostname/IP и свежесть** подтверждений. Разные результаты внутри группы должны понижать групповую уверенность/разделять группу; ручные локи, scope и точные результаты выше групповых. Группировку использовать локально; **не отправлять сырые hostname, IP или легко восстанавливаемый CDN-суффикс на публичный Redis-сервер**.
6. Без тестов на нормализацию, коллизии, версионирование групп, переход `rr1 ↔ rr2`, `index ↔ index2` и ложную переносимость **не считать** группировку готовой.

#### B3.4. Исключения Ramp на уровне SYN и конфликтующие назначения

1. Поддерживать минимум два управляемых набора: `googlevideo_pool` (**Ramp по умолчанию**) и `googlevideo_ramp_exempt` (**исключения с TTL**). Исключения должны обрабатываться **раньше** маркировки Ramp и воздействовать на SYN и все дальнейшие стадии конкретного нового flow. Исключённый IP остаётся на штатном TCP/TLS треке, а не выходит из production `nfqws2`.
2. Если один IP одновременно связан с `host A: Ramp required` и `host B: plain sufficient`, **нельзя безопасно выбрать per-domain на SYN**. В консервативной Beta 1 сохранить Ramp для этого IP, поставить `Conflict`, не пытаться подменять состояние посреди TCP-сеанса. То же при недостоверной DNS↔IP связи, смене адреса, ECH/DoH или неполном наблюдении.
3. Исключение может распространяться только на подтверждённый destination IP (и **client scope**, если он достоверно определяется до SYN и поддерживается firewall; иначе общий LAN opt-in). Истечение DNS TTL / смена привязки / новый конфликтный hostname снимает либо требует переподтверждения исключения. У самого исключения независимый TTL и hysteresis: не переключать его туда-сюда после одной неудачи.
4. Если IP пришёл из центрального пула, но пользователь его не посещал, Ramp остаётся включённым, **никаких фоновых проб**. Если IP исчез из валидированного пула, не сохранять для него скрытое beta-правило и не затрагивать прочие подключения.
5. Проверить совместимость с пользовательским `Z2R_WSSIZE_RAMP_ENABLE=1`: **не перезаписывать ручную настройку**, не менять значение в config.default при появлении/исчезновении исключений. При ручном безусловном Ramp beta-исключения либо управляются только после явного разрешения на частичное отключение, либо не применяются; показать конфликт.
6. На OpenWrt использовать nft set/mark при корректной очередности hooks; на Keenetic — совместимый ipset/iptables подход только если доступен и проверен на реальном устройстве. **Не предполагать автоматически наличие `ipset`/nft set** на всех Entware-сборках. При неподдерживаемой платформе не объявлять функцию «динамическое отключение Ramp» работающей.
7. Изменение наборов должно касаться **только новых соединений**; conntrack/маркировка уже открытого потока остаётся согласованной, что особенно важно для `wssize_ramp` full. `disable`, `pause`, fw4 reload, NDM rebuild, SIGKILL и reboot восстанавливают предыдущее поведение и не удаляют чужие правила.

**Приёмка PR-B3:** после подтверждённой нужды в Ramp и явного согласия beta-контроллер применяет Ramp к **всему известному Googlevideo IP-пулу**. Пользователь обращается к нескольким различным Googlevideo host/IP. Без ручного запуска Supersweep фоновые пробы сравнивают `Ramp ON/OFF` с одинаковой TLS-стратегией и реальными медиа; два подтверждённых `plain` результата создают временное **исключение только для безопасно классифицируемого IP**, другие непроверенные IP остаются Ramp. Для `rr1-index` и `rr2-index` переиспользуется групповая очередь кандидатов; `rr1-index2` остаётся отдельной группой. При общем IP для несовместимых host сохраняется Ramp и выводится `Conflict`. Production-клиент идёт по обычному TLS треку на exempt-IP; после TTL/деградации Ramp восстанавливается. Все тесты — через изолированную queue с подтверждением SYN/late ACK; результаты с некорректным route/ссылкой — `INCONCLUSIVE`; ручные настройки и чужие правила не тронуты.

Batched ingestion с jitter; precomputed rankings и редкий worker. Дополнительную память V2 сначала ориентировать на 32–64 МиБ, но установить лимиты после измерения на реальном host, сохраняя запас под RDB fork/CoW.
9. `-UploadStatistics` и `-UseSharedRankings` остаются **независимыми opt-in**. Протоколы не принимают клиентский произвольный UUID как идентификатор источника; per-install credentials, дедупликация, cap вкладов, idempotency и отзыв согласия сохраняются.
10. Production stats-host не трогать без отдельного разрешения. Сначала тестовая VM с совместимостью старых URL и реальным HTTPS, потом отчёт по RAM/CPU/пиковым нагрузкам, процедура backup/rollback.
11. Данные группировки Googlevideo (`group_id`, `host+ip`, DNS TTL, Ramp-exempt) — **локальные**, не добавлять их как сырые измерения в Redis. Централизованная статистика может учитывать агрегированный `gv_tcp_plain` / `gv_tcp_ramp` / `gv_tcp_ramp_syndata` отдельно от QUIC, без публикации точных CDN-имён. Не смешивать наблюдения с и без Ramp даже при одинаковой TLS-стратегии.

**Приёмка:** один и тот же номер `strategy=7` с разными blob/clone/Ramp не совпадает по semantic ID; перестановка номеров не меняет fingerprint при неизменной семантике; QUIC не попадает в TCP-рейтинг; 2048 заполненных комбинаций не создают неконтролируемой памяти или потери ранее опубликованных рейтингов; Redis недоступен — локальный поиск работает.

### PR-B6. Исследование, обновление качества и UX Beta — **P1**

1. Сохранить low-priority Explore: один probe на роутер, не чаще текущего бюджета (ориентир 120 с), пауза при высокой загрузке ПК/роутера/канала. Срочная проверка должна вытеснять фоновую **без** уничтожения чужого владельца очереди.
2. В режиме Ramp-first выделить отдельный **низкоприоритетный фоновый Ramp-аудит**: брать только реально наблюдённые `host+ip`, дедуплицировать по CDN-группам, сравнивать `Ramp ON/OFF` на одном медиа-рецепте и отключать Ramp на подтверждённых безопасных IP. Приоритет тестов и расписание не должны создавать постоянный перебор всего Googlevideo-пула; без доступного проверяемого media URL — `pending`, а не ложный вердикт.

Сохранять cursor и coverage, выделять часть слотов разнообразным **семействам** (fake/multisplit/hostfakesplit и т. п.) и устаревшим/недостаточно измеренным вариантам. Отложенная кооперация может использовать простой server-side priority list, **без** серверного диспетчера заданий. Для Beta 1 достаточно локального устойчивого Explore и честной статистики; удалённое координирование не блокирует выпуск.
4. В Watch различать `seen`, `suspected_failure`, `needs_verify`, `active_rule_degraded`, `cooldown`. Не генерировать FastSearch на каждое соединение; при переполнении очереди не терять срочные запросы из-за новых `seen`.

6. Кнопки: «Проверить ресурс», «Повторно проверить», «Сбросить авто-правило», «Приостановить», «Полностью отключить». По умолчанию безопасный OFF; тестовое применение невозможно без отдельного согласия.
7. Не требовать открытия интерфейса на WAN. Роутерные токены/парное подключение держать отдельно от серверных токенов. Предупреждать об истечении 30-дневного pairing token заранее, иначе «самоподбор» внезапно прекратится. Не продлевать полномочия бесконтрольно.

9. Сформировать машинно-читаемые метрики: time-to-first-confirmed, candidates_checked, fast/deep, success_after_apply, revalidation_failures, flip-flops, media throughput Mbps, inconclusive reasons, CPU/RAM/WAN overhead.

**Приёмка:** пользователь понимает, что функция требует работающего агента, в любой момент может вернуться к прежнему режиму; ошибки не маскируются «стратегия не работает», история браузера не утекает на stats-хост.

### 5.1. Состояние пробы

Рекомендуемые поля (при изменении схемы повысить версию и обеспечить явную миграцию):

```json
{
  "schema_version": 2,
  "test_id": "opaque-id",
  "target": {
    "hostname": "rr1-index.googlevideo.com",
    "group_id": "gv:rr:index",
    "destination_ip": "203.0.113.10",
    "ip_family": "ipv4",
    "transport": "tcp",
    "profile_id": 2,
    "scope": "default"
  },
  "recipe_id": "googlevideo-tcp-media-v1",
  "treatment_variant": "gv_tcp_ramp",
  "ramp_policy": "pool_default",
  "strategy": {
    "local_number": 37,
    "semantic_fingerprint": "sha256:...",
    "catalog_version": "sha256:..."
  },
  "path_evidence": {
    "test_queue_owned": true,
    "tuple_seen": true,
    "strategy_ack": true,
    "syn_stage_confirmed": true,
    "data_stage_confirmed": true
  },
  "transport": "OK",
  "application": "OK",
  "overall": "SUCCESS",
  "reason": "media_ok",
  "confirmation_level": "media",
  "duration_ms": 0,
  "bytes_received": 0
}
```

**Это проект расширения**, а не существующий рабочий контракт; реальные ключи/enum определить после ревизии совместимости v1 API. Адрес `203.0.113.10` в примере — документационный TEST-NET, **не** разрешённая тестовая цель. В публичную серверную статистику **не** отправлять объект целиком: удалить hostname/IP/test_id/путь и оставить только агрегаты по допустимым измерениям.

### 5.2. Правило переходов

| Наблюдение | Итог пробы | Переход поиска | Влияние на лок | Влияние на Redis |
|---|---|---|---|---|
| Подтверждённый корректный media или app | SUCCESS | Остановить / подтвердить | Допустимо применить в точном контексте | Учесть успех с recipe |
| TCP/UDP timeout при подтверждённом тестовом пути | INCONCLUSIVE | Следующий кандидат в пределах бюджета | Не менять | Не снижать рейтинг |
| Не совпал tuple / чужая NFQUEUE / неправильный ACK | INCONCLUSIVE | Остановить, исправить инфраструктуру | Не менять | Не отправлять |
| HTTP 429 / временный 5xx / подписанная ссылка истекла | INCONCLUSIVE | Отложить эту цель | Не менять | Не снижать рейтинг |
| Повторяемый отрицательный результат B между подтверждёнными A | FAIL (высокая доказательность) | Следующий кандидат | Не снимать рабочее правило по единичному факту | Возможен агрегированный негатив |
| Работает TCP fallback, но не QUIC | `quic=INCONCLUSIVE/FAIL`, `tcp=SUCCESS` по своим рецептам | QUIC продолжить/отложить | Не включать глобальный UDP drop | Не засчитывать QUIC success |

**Не использовать один общий статус `HTTP 200 = OK` для всех сервисов.** Раздельно валидировать: маршрут, транспорт, прикладную операцию, достаточность передачи данных, соответствие клиента и назначение.

### 6.2. Реальная проверка на OpenWrt и Keenetic (go/no-go)

Для **каждой** целевой платформы:

1. Сравнить тестовый TCP и штатный TCP на одном hostname/IP: q65535 (тест) и production queue 300 (обычное соединение).
2. Аналогично UDP/443 HTTP/3: test q65535 и production queue, без захвата обычного трафика.
3. Ramp: увидеть обработку **SYN, ClientHello и поздних ACK**, получить настоящий Googlevideo media verdict; сравнить plain и ramp. Дополнительно продемонстрировать **Ramp-first на всём известном Googlevideo IP-пуле**, фоновую проверку **только реально посещённых** назначений, создание и отзыв точных IP-исключений без рестарта production `nfqws2`.
4. Проверить plain TCP, Ramp full/lite и `syndata` opt-in, profile-5 QUIC и HTTP/3-only; отдельно показать **неоднозначный IP с двумя разными Googlevideo hostname** (Ramp сохраняется) и **`rrN` CDN-группы** (кандидаты переиспользуются, отключение Ramp без exact-IP проверки запрещено).
5. `fw4 reload` / NDM rebuild **во время активного lease**, `SIGKILL nfqws2`, `SIGKILL controller`, обрыв агента, истечение lease, router reboot/power loss, recovery от чужих правил и занятых NFQUEUE.
6. Проверить route через обычный WAN и (отдельно) PBR/VPN/offload, либо явно запретить непройденную топологию; нельзя распространять результат теста с другого WAN как эквивалентный.
7. Проверить official и fork `nfqws2`, BusyBox/старый Entware iptables, файлы/права, отсутствие `stat`/`od`, port binding Windows PowerShell 5.1.
8. Длительный прогон (не только 4 секунды): CPU/RSS тестового и рабочего `nfqws2`, нагрузка контроллера, latency пользовательских соединений, RAM, запись flash, нагрузка WAN.
9. Проверить двух агентов одновременно и конкуренцию с Supersweep: очередь/lock у одного владельца, приоритет срочного probe и безопасное освобождение ресурсов.
10. По окончании: все временные firewall-правила/очереди/lock-и удалены, production PID/локи/настройки остались как были.

**Не запускать destructive tests, постоянные firewall hooks или deployment на пользовательских роутерах и production stats-host без явного разрешения владельца.** При отсутствии доступа — оставить hardware gate `NOT VERIFIED`, не делать фиктивную приёмку.

### 6.3. Бюджет по умолчанию (настраиваемые стартовые ориентиры)

| Объект | Стартовый бюджет | Поведение при превышении |
|---|---:|---|
