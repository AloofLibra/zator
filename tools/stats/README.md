# Подсказки из Redis

Роутер получает `GET /z4r/recommendations.tsv?provider=…` с сервера статистики,
без GitHub и без скачивания сырых прогонов. CLI и WebUI используют один кеш
`extra_strats/cache/recommendations.tsv`: 24 часа, включая неудачные запросы.
Обновление ленивое; старые данные при сбое сохраняются с предупреждением.
Ответ ограничен 8 КБ и 17 строками. В главное меню сетевой запрос не добавлен.

## Выборка

- Только завершённые суперсвипы с полной матрицей всех четырёх блоков.
  `state=applying` допустим: клиент отправляет архив до интерактивной сводки.
  Прерванные, неполные и summary-only архивы не участвуют.
- Провайдер определяется по бренду, точным алиасам и известным ASN из
  `data/providers/asn.txt`. Город не дробит выборку; неизвестные ASN не угадываются.
- Порог — 10 разных UUID. Для топа берётся последний завершённый прогон
  каждого UUID для провайдера: частые повторные загрузки не увеличивают его вес.
- По каждому блоку — до трёх стратегий с ненулевым зелёным результатом,
  сортировка по доле зелёных проверок, затем по числу UUID и номеру стратегии.
  `samples` стратегии — число UUID, а не доменных проб; в RKN один UUID
  проверяет несколько доменов. Успешность считается по всем доменным пробам.
- Clone/classic сравниваются отдельно по каждому блоку: последний завершённый
  прогон UUID в каждом режиме, сумма зелёных / сумма всех проб, не среднее процентов.
  Подсказка о клонах появляется только при строго большей успешности и минимум
  трёх UUID в каждом режиме (плюс общий порог 10). Без метаданных режима — classic,
  как в клиенте до появления clone. Включённому clone подсказка не показывается.
- Номера стратегий между версиями конфигурации могут измениться; архив пока не
  содержит версии схемы стратегий. Версия zapret2 её не заменяет. WebUI отбрасывает
  номера вне текущего диапазона и никогда не применяет рекомендации автоматически.

## Сервер

`recommendations.py` устанавливается рядом с существующим `/opt/z4r-stats/server_redis.py`.
`server_redis.patch` — точечная интеграция нового публичного GET, не замена коллектора.
База `asn.txt` устанавливается рядом с ними, либо путь задаётся через
`Z4R_STATS_PROVIDER_ASN`. Существующие маршруты/авторизация коллектора не меняются.

Добавление к nginx snippet:

```nginx
location = /z4r/recommendations.tsv {
    proxy_pass http://127.0.0.1:17683/recommendations.tsv$is_args$args;
}
```

Перед применением: резервные копии коллектора и snippet, проверка патча на текущей
версии, `python3 -m py_compile`, `nginx -t`. После рестарта коллектора и reload nginx:
проверить `/z4r/health` и новый endpoint через внешний клиент.

Redis хранит один компактный агрегат всех провайдеров с TTL 86400 секунд.
Холодный запрос читает существующий индекс и хеши через pipeline; последующие
запросы любых провайдеров читают только агрегат. Refresh защищён process/Redis
замком с lease и атомарной публикацией. Никакие UUID/домены не возвращаются клиенту.
Ограничение существующего хранилища — последние 500 загрузок. Для более длинной
истории нужно расширить retention коллектора или поддерживать накопительный
агрегат при загрузке; роутер менять не потребуется.

## Проверки

```sh
python tests/recommendations_server_test.py
ZATOR_STATS_SERVER=/path/to/server_redis.py python tests/recommendations_server_test.py
bash tests/recommendations_smoke.sh
cd webui-src && node scripts/check-recommendations.mjs && npm run check && npm run build
```

Без `ZATOR_STATS_SERVER` интеграционный HTTP-тест явно пропускается;
остальные серверные проверки независимы от развёрнутого коллектора.

## Googlevideo IPv4 feed

`googlevideo_ips.py` делает отдельный Redis feed только для IPv4 адресов,
полученных для конкретных поддоменов `*.googlevideo.com`. Источники hostname:

- `raw:media-meta.json` в уже загруженных SuperSweep архивах. Это метаданные
  реального видеопотока (`cdn_hostname.audio/video`); подписанные URL и токены
  не читаются и не сохраняются. Эти архивы доступны только если пользователь
  включил существующую отправку статистики.
- `data/googlevideo/seed-hosts.txt` — ручные начальные hostname. В него можно
  добавить только конкретные полные имена, по одному на строку.
- Опционально `youtubeparsed` из no-google; каждая строка проходит ту же строгую
  проверку, так что `youtube.com`, `ytimg.com`, wildcard и посторонние домены
  отбрасываются.

`refresh` опрашивает hostname через Google, Cloudflare и Quad9, сохраняет пары
hostname/resolver/IP с timestamp в Redis (`z4r:googlevideo:v1:*`). Публичный
ответ содержит только globally-routable IPv4 наблюдения не старше 7 дней;
hostname живут до 45 дней, сырые DNS наблюдения — до 30 дней. Никакие данные
пользователя/UUID не отдаются в feed.

Для развертывания скопируйте три файла в /tmp stats-сервера (seed переименуйте
в googlevideo-seed-hosts.txt) и запустите deployment-скрипт от root:

```sh
python3 /tmp/deploy_googlevideo_server.py --stage-dir /tmp
```

Скрипт делает резервные копии целевых файлов, добавляет публичный
/googlevideo-ips.txt в коллектор, прокси-маршрут nginx и блок в обзор
/zator/admin со списком hostname → IP, временем/resolver-ом наблюдения и
агрегированными CIDR. Затем проверяет Python/nginx конфигурацию, перезапускает
коллектор и dashboard и запускает первый сбор. Ежечасное обновление настроено
systemd timer-ом от пользователя z4rstats; серверу нужен исходящий UDP/53 к
Google, Cloudflare и Quad9.

Сбор hostname из архивов ограничен последними 500 записями индекса
SuperSweep. Текущая youtubeparsed может не содержать конкретных
googlevideo-хостов, поэтому стартовый адрес задаётся отдельным seed-файлом.

На OpenWrt сборщик слушает события `dnsmasq.dns` через UBus, на Keenetic/Entware
пассивно наблюдает DNS-ответы через `AF_PACKET`. Оба источника добавляют
локальный адрес в `z2r_googlevideo4` и отдельный временный spool в `/tmp`.
Spool не ограничен DNS TTL. При включённом согласии на телеметрию роутер
проверяет очередь раз в минуту и пакетно отправляет новые к центральному feed
IP не чаще одного раза за 3 часа. Успешно принятые записи удаляются; при ошибке
они остаются для повтора. Уже известные центральному списку IP отбрасываются.
Сервер проверяет публичный IPv4 формат, дедуплицирует адреса, хранит их 7 дней
и объединяет с DNS-наблюдениями в feed. Хостнеймы и UUID не сохраняются.

Для endpoint загрузки задайте при серверном развёртывании общий токен из
клиентской конфигурации: `deploy_googlevideo_server.py --ingest-token <shared-token>`.
Он записывается в `/etc/z4r-stats.env` как `Z4R_GOOGLEVIDEO_INGEST_TOKEN`;
nginx route для пакетного POST создаётся автоматически. Без этого токена endpoint
закрыт и локальная загрузка не будет принята.

На роутере CLI: «Настройки -> Дополнительно -> обновить центральный список».
Кеш скачанного ответа живёт 6 часов и заменяется атомарно только после проверки
формата, размера и адресов. Keenetic использует этот центральный список. На
OpenWrt пункты настройки dnsmasq помещают локально разрешённые
`googlevideo.com` адреса в `z2r_googlevideo4`; для iptables нужен `ipset` и
dnsmasq с ipset, для fw4 — dnsmasq с nftset. Экспорт локальных наблюдений
объединяет их с центральным файлом; частные/служебные адреса отбрасываются.

На данный момент feed предоставляется отдельно от `wssize_ramp`: включение
списка IP в NFQUEUE стратегию — отдельное изменение и не происходит скрыто.
