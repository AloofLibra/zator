# Zator Desktop Probe 0.1

Windows-приложение с Chromium и отдельным IPv4 HTTPS/WSS-контуром на роутере. Использует существующие стратегии установленного Zator. Рабочие `config`, `locked.tsv`, очередь и процесс zapret2 не изменяются.

Первичные аппаратные проверки проведены на **OpenWrt 25.12.4 / Cudy WR3000P / ARM64**. Keenetic/Entware и 128 МБ RAM пока не подтверждены: по указанию пользователя эти испытания отложены до получения устройства. Статус этапов и ограничения — [RESULTS](../docs/desktop-probe/RESULTS.md), решения — [ADR](../docs/desktop-probe/ADR.md).

## Сборка на Windows

Нужны Node.js 22+ и Go 1.27.3. На роутере Go, Node.js и Python не нужны.

```powershell
./desktop-probe/scripts/build-router.ps1
cd desktop-probe/app
npm ci
npm test
npm run smoke
npm run pack
```

`app/release/ZatorDesktopProbe-win32-x64/ZatorDesktopProbe.exe` — запускаемая portable-сборка. `dist/zator-desktop-probe-linux-{arm64,arm,mipsle,mips,amd64}` — статические router-бинарники. MIPS собирается с softfloat, ARM — ARMv7. Проверка сборки не означает подтверждение конкретного ABI/ядра; физически проверен ARM64 OpenWrt.

## Подготовка роутера

1. Нужны работающий Zator, `nfqws2`, root SSH, разрешённый SSH forwarding и проверенный host key. Используются штатные ключи/SSH agent. Приложение не принимает и не сохраняет пароль.
2. Скопируйте `settings.example.json` и сверяйте **каждое** значение с UID/GID, NFQUEUE, firewall и policy routing своего роутера. Пример содержит ресурсы тестового OpenWrt и не является универсальным назначением.
3. Для native nft выберите `backend: "nft"`; требуется штатная таблица `inet zapret2` с `postnat_hook`/`prenat_hook`. Для Keenetic предусмотрен `backend: "iptables"`, но его аппаратные испытания ещё не выполнены. Pre-NAT и нестандартный desync/post-NAT mark отклоняются.

WAN задавать не нужно: агент читает активные IPv4 default routes основной таблицы ядра. Тип подключения и имя устройства не важны: DHCP, статический IP, PPPoE/PPP, VLAN, USB-модем используют один механизм. Выбираются доступные маршруты с минимальной метрикой; равнозначные выходы и multipath учитываются вместе. Старое поле `wan` игнорируется. После смены подключения новый запуск автоматически использует новый выход, без редактирования JSON. Смена маршрута во время проверки делает текущую попытку INVALID.

Маршрут каждого тестового соединения с его conntrack mark по-прежнему сверяется с активными default uplinks. Отдельный policy route в другой интерфейс не считается успешной WAN-пробой. Если VPN сам является основным default route, он является текущим uplink — проверка не доказывает прямой выход мимо такого VPN. При отсутствии IPv4 default route агент сообщает WAN_UNAVAILABLE. IPv6-only подключения остаются за пределами TCP IPv4 MVP.
4. Скопируйте соответствующий бинарник, настройки и `install-router.sh` в одну временную папку. Затем **на роутере**:

```sh
sh install-router.sh install ./zator-desktop-probe-linux-arm64 ./settings.json
/opt/zator/bin/zator-desktop-probe capabilities --json
```

Установщик проверяет файл настроек до остановки прежнего тестового компонента, сохраняет предыдущие component-файлы и пытается восстановить их при неудачной установке. Рабочий zapret2 не перезапускается. При ошибке cleanup файлы сохраняются для повторной попытки.

На Keenetic восстановление подключено к существующему `Entware/000-zapret2.sh` после рабочего firewall/client scope/Supersweep, только для IPv4 `mangle`. Перед установкой компонента нужен Zator с этим обновлённым hook.

Для OpenWrt предоставлен `firewall-openwrt.sh`: его можно вызывать из firewall4 script include **после создания таблицы zapret2** (`type=script`, `fw4_compatible=1`). Автоматическая правка UCI и перезагрузка firewall установщиком не выполняются. В первичных испытаниях потеря собственных правил моделировалась адресно; полный reload/reboot OpenWrt не проверялся. Если перед запуском потеряны тестовые правила (`TRANSPORT_CHANGED`), приложение автоматически выполняет отдельный `prepare-transport` и заново проверяет capabilities. Для старого агента потребуется обновление. При потере транспорта во время измерения попытка по-прежнему INVALID; автоматического продолжения старого прогона нет.

`prepare-transport` отказывает при активной сессии, блокирует параллельный старт через manager lock, проверяет конфликты и восстанавливает только собственные правила. Исправный транспорт не переписывается, generation не меняется; disabled-компонент не включается обратно. Если штатная таблица zapret2 ещё не создана, конфликтуют ресурсы или изменился несовместимый конфиг, подготовка возвращает ошибку. В интерфейсе восстановление показано отдельным состоянием.

## Работа приложения

Укажите SSH-адрес, пользователя, ключ/agent, HTTPS URL и номера стратегий. DIRECT выполняется первым. В длинном обычном списке повторяется контрольный DIRECT; связанный YouTube-проход начинает с пары DIRECT/DIRECT. Доступны только номера из живого профиля; автоматический выбор профиля читает установленные hostlists и не угадывает неизвестный домен по подстроке.

Для одного сайта выберите «Перебор → Все стратегии»: приложение само получит полный список номеров из живого профиля. Для общего прохода выберите «Полное сканирование · 4 профиля», задайте прямую ссылку на YouTube-видео, Discord URL и RKN HTTPS-сайты (до 32). Приложение проверит связку YouTube/Googlevideo, затем Discord и каждый RKN-сайт. Между целями — пауза 30 секунд.

YouTube всегда использует два профиля одновременно: YT для страницы/ресурсов и GV для `googlevideo.com`. При выборе этого сценария одиночный переключатель профиля отключается, список номеров применяется к каждому из двух профилей; «Все стратегии» берёт два независимых списка из конфига. После YT-1/GV-1 следующий проход — YT-2/GV-2, только если обе стадии были проверены. Если YT-2 не открыла страницу, GV-2 не оценивается и следующая пара — YT-3/GV-2. Когда YT закончились, оставшиеся GV проверяются с успешной YT (в том числе DIRECT, если он был рабочим). Если опорная YT перестала открываться, выбирается другая. Без рабочей страницы или подтверждённой попытки обращения к GV видео остаётся UNKNOWN «не проверялась» и не попадает в покрытие. Зацикливания на одной паре нет.

Результаты раздельные: профиль 1 получает оценку только открытия страницы, профиль 2 — только видео. Успех видео требует наблюдаемого прогресса и данных Googlevideo. Неуспех видео не ухудшает результат YT. В строке и JSON указана применённая пара. Ошибки вспомогательных ресурсов сохраняются в диагностике, но не ухудшают успешную стадию. Новый агент объявляет `youtube_pair_supported`; старый требует обновления, скрытого перехода на прежнюю однопрофильную пробу нет.

Прогресс показывает завершённые проверки и текущую цель. Компактная сводка группирует номера по профилю и сайту: сработали (OK), с замечаниями (WARN), не сработали (FAIL), не подтверждены (UNKNOWN) и ошибки проверки (INVALID). Списки номеров видны сразу, без раскрытия; DIRECT и опорные YT в сводку не входят. Непроверенные GV остаются UNKNOWN. Экспорт сохраняет подробное покрытие по числу сайтов с OK. При отмене сохраняются частичные результаты. Полное сканирование может занять несколько часов. При INVALID весь проход останавливается; уже собранные результаты доступны для экспорта. Автоматического применения локов нет.

Основное место занимает журнал с отдельными колонками страницы/видео, причинами вердиктов и общим номером пробы для связанных строк. Настройки запуска автоматически сворачиваются и блокируются во время прогона; их можно раскрыть для просмотра. Маленький предпросмотр раскрывается кнопкой, возвращается кнопкой или Escape; это изменение размеров того же браузера, без новой загрузки. Звук выключен, сворачивание не замедляет фоновые таймеры проверки видео.

Каждая стратегия получает свежие browser partition, TCP/TLS-соединения и тестовые процессы. Вся браузерная проба (загрузка, DOM и media-проверка вместе) по умолчанию ограничена 10 секундами; лимит 5–60 секунд меняется в форме. Готовый DOM проверяется без ожидания всех ресурсов. Таймаут или явный отказ загрузки не повторяются; неоднозначное DOM-условие повторяется не более одного раза. Сначала проверяется доказательство изоляции: таймаут не маскирует INVALID. После подтверждённого OK следующая пауза сокращается до 5 секунд; для пары YT/GV нужны оба OK, пока проверяются оба этапа. При WARN/FAIL/UNKNOWN остаются 15 секунд, для RKN — 30 секунд. Повтор неоднозначной попытки и переход между сайтами не ускоряются. Пауза показывается отдельным состоянием. Эти паузы и SSH/telemetry не входят в браузерный лимит. Firewall при start/set-strategy/stop не меняется.

- **Страница:** без обязательного CSS selector результат `UNKNOWN`. Selector задаёт проверяемое DOM-условие, а не универсальное доказательство работоспособности сервиса.
- **YouTube:** нужна прямая ссылка на видео; плеер опрашивается в пределах общего лимита, проверяются минимум 2 секунды прогресса `currentTime` и приход данных с Googlevideo. Проверка запускает видео без звука. В результатах отдельно показаны открытие страницы и подтверждение видео. Если страница ответила, но времени на функцию не хватило, результат UNKNOWN, а не FAIL. Открытие страницы само по себе не даёт OK для видео.
- **Discord:** нужны DOM-условие и полученные WebSocket frames от `gateway.discord.gg`. Авторизация/капча дают `UNKNOWN`; голос/UDP не проверяются.
- **Ручной режим:** до пяти минут на осмотр; оценка хранится отдельно и не меняет автоматический verdict.

Детектор авторизации учитывает только отображаемые поля пароля и CAPTCHA с ненулевым размером, а также признаки страницы входа/challenge в заголовке. Скрытая форма входа в обычной публичной странице (например, anidub.com) не означает `AUTH_REQUIRED`. Скрытие через предков, `visibility` и `opacity` учитывается; остальные требования DOM, TLS и доказательства трафика сохраняются.

Потеря очереди/процесса/SSH, смена поколения firewall или маршрутов, неверная метка, чужой маршрут и откат счётчика очереди дают `INVALID`. Если транспорт работает, но конкретная проба не имеет полного совпадения proxy tuple → conntrack → Lua invocation, результат `UNKNOWN / FLOW_EVIDENCE_INCOMPLETE`: он не считается успехом, но не прерывает остальные стратегии. Неожиданный переход на другой домен также даёт `UNKNOWN`. Один HTTP 200 не даёт `OK`.

Неудачное TCP/SOCKS-подключение (`CONNECTION_NOT_ESTABLISHED`), отсутствие новых queue packets или недоказанная свежесть — также UNKNOWN без зачёта успеха. Это не означает, что стратегия проверена и не работает: до её TLS-обработки могло не дойти. В paired sweep GV при таком результате страницы не оценивается. Успех по-прежнему требует свежего соединения и роста счётчика вместе с остальными доказательствами.

Conntrack и Lua evidence публикуются отдельно. Итоговая telemetry при неполном снимке делает не более двух повторных чтений с паузой 100 мс; явные ошибки транспорта не повторяются и не скрываются. В отчёте сохраняются причина неполноты, числа совпавших потоков/вызовов/маршрутов и количество чтений. Ошибки чтения evidence возвращаются явно.

Тестовый packet mark восстанавливается из собственного conntrack bit даже для TCP-пакетов, которые ядро создаёт после закрытия сокета и которые уже не имеют UID прокси. Восстанавливается только тестовый бит, остальные mark bits сохраняются. Это исключает попадание поздних RST/ACK в production NFQUEUE. При отсутствии тестового conntrack bit или появлении production bit `FLOW_MARK_MISMATCH` по-прежнему останавливает прогон.

Доказательство собирается по конкретным хостам: обязательно подтверждаются документ и хосты, от которых получены Googlevideo data или Discord gateway frames. Незавершённый вспомогательный запрос не обнуляет подтверждённые соединения, но сам подтверждённым не считается. HTTP/2 reuse внутри свежей пробы допустим, когда router proxy доказывает новые соединения после переключения. При INVALID сообщение об остановке содержит конкретную причину.

Lua evidence сохраняет packet mark и фактический NFQUEUE `ifout` вместе с tuple/strategy/profile. Если к telemetry conntrack уже удалил закрывшееся соединение, его можно подтвердить по этому снимку: только при совпадении точного tuple и стратегии/профиля, корректном test mark и выходе через активный uplink. Без обоих полей историческое доказательство не принимается; существующая conntrack-запись с неверной меткой остаётся ошибкой. Смена поколения/маршрутов по-прежнему инвалидирует попытку. Число потоков из сохранённых снимков есть в `proof.packet_snapshot_flows`. Неподтверждённый документ или медиахост дают UNKNOWN без зачёта успеха и без остановки перебора.

JSON/Markdown экспортируются кнопкой. URL очищаются до origin, заголовки/cookie/тела запросов не собираются. Последний частичный отчёт сохраняется локально в Electron `userData/last-report.json`; SSH-настройки и owner token в него не входят. Снимок страницы сохраняется только по кнопке.

## CLI/RPC

Команды управления принимают JSON через stdin и выдают JSON в stdout. Owner — 64 hex-символа, session ID — 32. `DIRECT` в реализованном draft API обозначается числом **0**.

```text
capabilities
resolve-profile       {command, hostname}
start                 {command, owner, profile}
set-strategy          {command, owner, session, strategy}
status / telemetry    {command, owner, session}
heartbeat             {command, owner, session}
stop / recover        {command, owner, session}
```

Для связки: `start {profile:1, paired:true}`, затем `set-strategy {strategy:<YT>, gv_strategy:<GV>}` с теми же owner/session. Status возвращает `paired` и `gv_strategy`; изменение любого номера меняет поколение. Приватный конфиг содержит два отдельных nfqws2 profile, а Lua evidence дополнительно содержит номер профиля — одинаковый номер стратегии в другом профиле доказательством не считается.

Привилегированные локальные install-команды: `install-transport`, `reconcile-transport`, `uninstall-transport`; `admin-stop` завершает только сессию компонента. Они не входят в allowlist desktop SSH adapter. Unix control socket имеет mode 0600; управляющего HTTP-порта нет.

Отдельный `prepare-transport` доступен в фиксированном SSH allowlist только для подготовки между прогонами; он не является командой активной сессии и не заменяет её owner checks.

Lease — 90 секунд, heartbeat — 15. Linux guardian/subreaper завершает осиротевших тестовых детей при SIGKILL контроллера: собственный `setuid` nfqws2 сбрасывает обычный parent-death signal. После краша `recover` снимает stale socket только под lock; PID рабочего zapret2 не ищется и не завершается.

Удаление компонента:

```sh
sh install-router.sh uninstall
```

Полное удаление Zator также вызывает component cleanup. При неуспешной очистке каталог сохраняется. Настройки компонента включены в обычный backup. Внешний bootstrap `AloofLibra/z4r:z2r` продолжает работать без изменений; он не устанавливает необязательные Go-бинарники. Обновлённый NDM hook добавлен в core/offline payload.

## Проверки

```powershell
cd desktop-probe/router
go test ./...
go vet ./...
cd ../app
npm test
npm run smoke
```

Linux: дополнительно `go test -race ./...`. Физические тесты opt-in, требуют подготовленного компонента и свободной сессии:

Полный browser integration запускается как `electron . --probe-integration` с `ZATOR_PROBE_TEST_CONFIG` (JSON параметров формы с `scanMode: "supersweep"`), `ZATOR_PROBE_TEST_REPORT` (путь JSON) и отдельным `ZATOR_PROBE_TEST_USER_DATA` (существующий каталог). Он использует обычные таймауты и паузы приложения, сохраняет результаты после каждой попытки и пишет `<report>.summary.json`. PASS требует штатного завершения, отсутствия INVALID и строк для всех стратегий из capabilities; `untested` отдельно перечисляет GV, до которых не удалось дойти через рабочую страницу. FAIL/UNKNOWN отдельных стратегий не означают сбой сканера. Не запускайте одновременно с аппаратными тестами или другим сканированием.

```sh
ZATOR_PROBE_HARDWARE_BENCH=1 ./router-tests -test.v -test.run TestHardwareSingBoxCandidate
ZATOR_PROBE_HARDWARE_LIFECYCLE=1 ZATOR_PROBE_HARDWARE_FAULTS=1 ./router-tests -test.v -test.run TestHardwareAgent -test.timeout 150s
ZATOR_PROBE_HARDWARE_PAIR=1 ./router-tests -test.v -test.run TestHardwareYouTubePair -test.timeout 35s
ZATOR_PROBE_HARDWARE_PREPARE=1 ./router-tests -test.v -test.run TestHardwarePrepareTransport -test.timeout 35s
ZATOR_PROBE_HARDWARE_OWNERLESS=1 ./router-tests -test.v -test.run TestHardwareOwnerlessPacket -test.timeout 20s
```

`go test -c` создаёт `router-tests` под нужную GOOS/GOARCH. Эти проверки адресно меняют **только собственные** правила и завершают **только собственные** процессы; рабочие конфиги/локи проверяются по hash. Не запускайте opt-in hardware tests параллельно с приложением.

Не входят в TCP MVP: UDP/QUIC/HTTP3, IPv6, WebRTC, TUN/WFP, автоматическое применение результата в production, эквивалентность LAN-клиенту и подпись Windows-бинарника. TLS-проверка браузера остаётся включённой.
